# DR 客户服务门户与收货人入口 v0.1

2026-10-24 · 设计增补草案。来源为用户本次客户侧说明。当前仓库基线是 V1.4 评审稿及后续增补，不以说明中引用的 V1.2 回滚已确认的外部订单导入、KESS 收款、保险独立记账、COD 或财务结算需求。

## 产品定义与入口

建设货主／商户／企业客户门户和订单专属收货人入口。2026-10-25 用户确认主入口为 Telegram Mini App＋Bot 下单，桌面 Web 保留为企业客户辅助入口；不另建原生客户 App。详见[渠道增补](telegram-and-driver-app-scope-v0.1.md)，司机端目标同时包含 iOS／Android。现有手机网页仍只是交互原型。

货主是货物所有人或委托服务主体，不必是收货人。同一法人可能同时有付款义务和 COD 受益身份，但必须按授权关系分别读账。内部调度、司机、仓库、财务工作台不对客户开放。门户可以从智序小镇跳转，也必须直接访问；三维场景不是登录、下单或看账的前置条件。

| 阶段 | 开放能力 | 开启条件 |
|---|---|---|
| C0 配送最小入口 | 代录、通知、短期分享链接的脱敏配送进度 | 无须完整WMS；只读分享不带财务和个人地址 |
| C1 邀请制货主门户 | 本人订单、凭证、账单、付款申报、KESS入口、COD身份查询、异常与变更申请、企业成员权限 | 身份／货主成员权限、来源数据、内部审核链通过；KESS有独立上线门槛 |
| C1-RECIPIENT 收货交互 | 验证预登记收货人后，申请收货安排、反馈异常、登记收货声明 | 验证渠道、单订单授权及交付证据核对通过；只读分享链接不能执行这些动作 |
| C2 仓储协同 | 本货主库存、入库预报、出库配送申请 | 库存口径、权威WMS、并发预留与受理流程通过；未知库存不填0 |
| C1-ORDER 受控下单 | Telegram Mini App／Bot 共用草稿、报价、确认和提交 | 受邀客户身份、区域／价格／支付／容量／承诺校验通过；纳入首个客户闭环，未上线 |
| C3 自助服务 | 完整自助扩展、客户系统API、后续批量入口及企业内部审批 | 价格／区域／支付／容量／承诺重验与外部接入治理通过 |

阶段标识是开放顺序，不是删掉既有需求，也不代表已有接口上线。没有开放注册、复杂会员营销或公开整车实时地图。企业内部多级审批和批量业务审批仍单独细化，不在本轮机器契约假装完成。

## 核心规则

- 对象授权必须同时满足运营企业、货主账户、成员权限、业务关系及仓库范围。只检查 companyId 不足以隔离不同货主。接口不接收客户自报的 companyId/customerId 切换身份。
- 库存示例：账面100、预留20、隔离5、可申请75，前提是预留与隔离集合互斥且同一单位。数量附权威来源、版本及观测时刻。提交不是预留；受理时锁定库存再检查。客户入库预报不是仓库实收。
- 改地址／改时间只生成申请。接受前重评区域、费用、装载、全部原承诺并取得必要客户同意；不能直接改路线或刷新原承诺时钟。
- 收货确认绑定订单、收货人授权、交付记录及证据。不是任意人点击分享链接就能完成签收；少货、货损、错货、拒收有独立入口。异常申报不自动认责、赔款或减免。
- 货主只看本主体费用与资金归属。不能看合作采购价、内部利润、他人银行流水／COD或内部敏感审计信息。财务读权限与付款申请、账单确认、成员管理分开。
- 付款截图仍为申报；KESS成功是渠道收款，银行到账和业务核销另核。客户认可账单只写客户确认状态，不替代内部经办／复核／审批，也不把未结变成结清。

## 接口与验收

[机器契约及开发说明](../../contracts/README.md)分别定义 customer、merchant、partner、recipient、public、warehouse 和内部 ops 分组；中控 integration 继续只读。所有已有 Demo 路由及角色切换仍只是演示，不自动成为授权后台。

最低验收：A货主不能访问B的订单／凭证／账单；只读成员不能付款或改成员；分享过期/撤销统一404；收货人验证码不能用于另一订单；重复申请不重复预留或派单；改地址重新受理；上传凭证不自动到账；客户确认不替代内部审批；无库存来源明确未知；三维入口不可用时仍可直接办业务。

本轮更新的是需求与接口设计，没有新增生产开户、真实支付操作、原生App开发任务或公开门户部署。

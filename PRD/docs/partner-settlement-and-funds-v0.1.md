## 1 结论与业务口径

建设“合作方结算与资金管理”，展示资金沉淀，但不把延迟付款作为主要盈利或降本方式。付款周期用于确定对账和付款安排，不能任意拖延已到期款。平台提成也不等于扣除税费、保障责任和运营成本后的利润。

区分两个时钟：客户付款条件是预付／获批月结；承运方付款条件是合作协议约定的结算周期。两者不能直接绑定。月结客户未回款时，已到期的合作方应付款仍保留，按协议支付并展示平台垫资缺口，不能自动改到期日。

首期只处理真实配送产生的应收与应付款，不新增客户充值储值、余额转账、理财或借贷。司机“可提现收入”是配送收入结算入口，不是可充值或支付的通用钱包。平台究竟是承运合同主体还是代收代理，尚待合同与资金流核实，本文不推断法律或会计身份。

## 2 建议周期及计时方式

| 对象 | 建议草案 | 页面应展示 |
|---|---|---|
| 独立个人承运方 | 周结；本地时间周日 23:59:59 截止，本周合格且已申请款纳入下周三付款批次 | 待核验、可申请、申请中、已批准、预计付款日、已支付 |
| 合作车队／配送企业／快递企业 | 按合同月结；自然月末截止，次月 10 日为建议付款日 | 本期明细、对账差异、确认账单、应付日、已付与未付 |
| 自营司机 | 沿用司机收入及人工审核提现流程；是否采用同一周结策略另由协议确定 | 不因个人身份自动套用合作承运价或重复生成收入 |

统一以 Asia/Phnom_Penh 时区计算。建议付款日遇非银行工作日顺延到下一银行工作日，节假日日历和实际银行截止时间需运营配置；页面展示具体日期，不只显示含义不明的“T+7”。提前付款仅为人工批准例外，不新增提前结算收费。

“合格”是履约事实已核验、应付金额与收款主体已确认、相关款项无待裁定争议；不要求所有客户账款已到账。履约完成、财务核验、账单截止、合同到期、预计付款和实际付款分别存储。

账期必须明确从履约还是核验起算；建议按履约所属期归集，记录核验时间。过截止后才核验、迟交凭证或财务漏审的款进入补充处理，保留原所属期和合同到期日，不自动推迟整个月。超过约定核验期限必须提示负责人处理，不能用“待核验”无限延付。

个人申请沿用已确认的“可申请提现、财务人工审核”。未申请余额继续显示，可提示申请，不能充作平台收入；合同如有无须申请的强制付款期限，系统须提醒财务履行。公司作为签约收款主体时，给公司付款，不再给其司机重复入账。

## 3 最小结算闭环

### 3.1 按主体设置账期

配置对象是合同中的客户／合作单位／独立个人，不是登录账号。同一单位的多个操作账号共享该主体的有效规则；同一主体兼有客户和承运方身份时，应收、应付各自配置，不能自动抵销。

| 设置项 | 约束 |
|---|---|
| 结算方向和主体 | 客户应收／承运应付分开；企业内授权范围隔离 |
| 结算方式 | 预付、日结、周结、月结、每 N 天或逐单 T+N；预付客户不能因设置月结日期直接获得赊账资格 |
| 起算及截账 | 明确履约／核验等起算事件、周期锚点、截账时间和时区；每 N 天不能与逐单 T+N 混淆 |
| 出账日和收付到期日 | 分开设置，例如月末截账、次月 2 日出账、次月 10 日到期；这些是示例而非默认承诺 |
| 日期调整 | 日历日／工作日明确；每月 29–31 日遇短月的处理方式必须选定并预览；节假日顺延遵循协议 |
| 提醒规则 | 出账日、到期前 N 天、到期日、逾期后 N 天及后续间隔；提醒只触发任务，不自动加收罚金 |
| 财务责任人 | 主负责人、替补和升级接收人；通知渠道及授权联系人，停用账号必须重新分配 |
| 协议与版本 | 生效日期、适用币种、批准记录、策略来源；保存前预览接下来三个周期的截账／出账／到期日期 |

单独约定优先于主体已选模板；无有效规则显示“待配置”并进入财务待办，不默认为立即到期或无限期结算。新版本仅对约定生效的业务使用；变更已出账款的到期日需单独批准、留痕并告知相关人员，不能批量改规则后抹除逾期。旧任务同步撤销或替换但保留记录。中途换规则时预览受影响明细，禁止重复或漏计期间。

### 3.2 财务到期任务与催收

| 触发条件 | 系统任务 | 财务完成条件 |
|---|---|---|
| 出账日到达 | 生成唯一待出账任务，汇总账单草稿和异常明细，通知责任人 | 核对并确认正式对账单；有误则退回处理，不直接标已出账 |
| 客户应收将到期／当天到期 | 创建收款提醒任务，显示应收、已核销、待核款和剩余金额 | 财务确认是否发送付款提醒，记录接收人和渠道 |
| 客户应收逾期且有可催收余款 | 生成催收单草稿，通知财务并按规则升级 | 核对后发送／登记联系结果、客户承诺付款日与下一跟进时间 |
| 合作方应付到期 | 创建付款待办，显示已批准、待审核和资金缺口 | 审核及人工付款、独立核验结果；不能给合作方生成客户催收单 |
| 有到账／争议／付款结果变化 | 重算余额并更新未完成任务 | 全额核销关闭催收；部分核销只催剩余；已支付关闭付款任务 |

账单流程：待出账 → 草稿 → 财务确认 → 待发送／已发送 → 部分结清／已结清；存在争议时保留账单和分项差异，不删除原账。财务对账单不等于法定税务发票，开票流程另行明确。出账日按时汇总可核验项，缺凭证项单列，不伪造金额也不拖住无争议部分。

催收单引用已确认账单、到期日、币种、付款记录及当前可催余额，不新建第二笔应收。发送前再次检查余额、权限和账单版本；已付款待核验部分进入核查暂缓，争议部分进入争议处理，无争议余款可继续催收。客户承诺付款日仅作为跟进日期，不自动修改合同到期日。逾期不自动罚息、扣司机款或取消运输中的订单。

首期自动执行内部财务提醒和草稿准备；对外账单／催收单由财务确认发送，不默认开通短信或自动批量催收。内部站内通知有深链、责任人、处理期限和失败记录；通知已读不等于任务完成，待办持续保留。外部渠道发送失败保留重试入口，不标成功。

任务按企业、主体、方向、逻辑账期或账单、提醒阶段去重；规则版本是来源快照，不可用换版本绕过去重。调度任务重复运行和服务重启不重复生成账单／催收单，遗漏任务按原时间补建并标延迟，通知合并避免补发轰炸。只有有权限的财务可确认账单和对外发送，调度与中控只读。

### 3.3 承运应付与付款

1. 合作方准入：确认企业／个人身份、合同收款主体、脱敏收款账户、币种、承运价或分成约定及结算策略版本。变更只影响约定生效后的业务；历史账项保存快照。
2. 履约核验：签收或核准的退回服务形成应付依据；外部快递上报签收仍需内部核验。客户退款不自动扣承运方报酬，保费不参与配送费分成。
3. 账单生成：按主体、币种、期间汇总未结明细。合作协议可用固定承运价或分成，不能把个人司机比例强套所有企业。明细显示订单、服务、原额、批准调整、已付、剩余、到期日。
4. 核对及争议：只冻结有具体依据的争议金额；无争议部分继续结算。无操作不自动当作合作方认可；付款不消灭尚未解决的差异。每笔争议有负责人、原因和下一处理时间。
5. 批准及付款：申请／账单锁定同一应付余额；财务审核后人工付款，付款人与结果核验人分离。记录银行结果、凭证和实际金额，部分付款保留余款。
6. 对账关闭：确认成功才减少未付余额。处理中／结果未知先查原付款，不释放预留、不重付；明确失败且确认未出款后才允许解除预留或重试。所有调整保留原记录。

同一应付不能既走司机提现又走合作方批量付款；以业务来源和结算归属统一控制。结算批次不是第二套钱。银行账户变更不覆盖已批准付款快照，必须重新核验后调整。

## 4 资金沉淀与资金缺口

后台入口建议为“财务 → 结算与资金”，拆分菜单：结算规则、财务待办、客户应收、合作方应付、个人申请、付款批次、资金日历。财务待办内用 TAB 切换待出账／待收款／待催收／待付款／异常；列表显示主体、方向、金额、账期、到期日、负责人和下一动作。合作方只看自己的明细；调度只看履约相关提示，无权更改账期或付款结果。

资金看板按币种分别展示：

- 银行已核实余额、渠道未到账款及余额更新时间；未到账不冒充可支付现金。
- 未履约客户预付款、已履约承运方未付、保费待划转、已批准退款、其他有依据的资金占用。
- 今天／未来 7 天／未来 30 天到期付款，以及预计客户回款；预计回款和已经到账分开。
- 受限资金与可用于对应付款的资金来源、资金缺口、已逾期金额、人工处理负责人。

这些分类不能直接相加扣减：同一收款随履约转换为承运应付等用途，不能既按全额“未履约预付”又按“承运应付”重复占用；付款预留、提现申请与其底层应付也只计算一次。正式会计科目和总额／净额收入确认由合同角色和会计审核决定。

流动性预测按时间逐笔滚动：期初可用于该用途的已核余额 + 情景内预计到账 − 到期净支付。基准情景仅使用已核实资金；预测情景另列并模拟延迟到账。缺口显示为负数和具体日期，不用截断为零掩盖问题。不得以可支付某笔合作方款的余额推导为可用于广告或其他运营支出的余额。

资金沉淀估算只用于理解时差：在业务平稳的假设下，平均承运未付余额约为“每日新增应付 × 从应付产生到付款的实际平均天数”。例如每日新增应付 1,000 USD、平均延迟 7 天，则约 7,000 USD；这是合成估算，不是收入、利息收益或可动用额度。周结不等于每笔延迟 7 天，月结也不等于每笔 30 天；截止日、核验、申请、节假日都会改变平均值。

## 5 方案判断

### Phase 1 — Strongest Case Against

**Known Facts：**用户已确认先付款或获批月结再派单、保险独立不分成、个人提现人工审核；当前材料没有真实日订单量、合作方签署账期或资金余额证据。

**Assumptions：**个人能接受周结，企业能接受月结，平台有独立资金覆盖月结客户的垫付。均待验证。

**Inferences：**预收款与延期结算可能产生资金沉淀；但客户月结、退赔和付款集中到期也可能产生净资金缺口。

**Unknowns：**合同主体／代理身份、实际承运利润与账期报价、合作方现金需要、收款渠道限制、适用监管要求。

最强的三个失败原因：

1. 把负债余额当运营资本，遇到回款延期和集中结算时不能按期付款。
2. 为沉淀延长账期导致合作方加价、拒单或离开，反而增加配送成本。
3. 未确定收款身份就实现代收、储值或资金混用，产生合同和监管风险。

### Phase 2 — Strongest Case For

最强的三个成立理由：一是固定账期让合作方与财务都能预期付款；二是按订单核对、部分争议隔离和批量付款可减少重复支付及人工差错；三是先以账期台账和人工付款试行，未上线储值与自动划款，调整策略的成本低。支持的是清晰结算和现金预测，不是靠拖欠获得收益。

### Verdict

采用可追溯的周期结算和资金预测；个人周结、企业合同月结作为候选。不要把“资金池可供扩张”作为已成立的商业结论。

### Confidence

80%：对“先建结算闭环、隔离应付用途”的判断信心；不是对具体周期接受率或监管适用性的统计估计。

### Why

与已有预付、合作承运、独立保险及人工提现链一致；真实资金规模和合作条款尚无证据，不能推导可支配资金收益。

### Key Variables

合作方接受的账期及承运价格；客户实际回款与退款节奏；合同身份和资金使用限制。

### Largest Unknown

平台实际收款及承运合同结构，决定何种资金属于平台以及支付义务何时到期。

### Reversal Condition

如合作方不接受周期或因此明显涨价，改短周期；如现金预测显示到期缺口，先补足自有流动性或收紧月结准入，不以延付解决；如收款结构需持牌服务，改由合适的持牌支付方完成收付并重新评审流程。

## 6 最小验证与未验证边界

- **Hypothesis：**不依赖未来新客户预付，仍能按期支付合作方；结算批次不会重复占款或付款。
- **Test：**两天内用一个完整月份的合成账本重放个人周结／企业月结，包含客户月结晚到、退款、争议部分释放、节假日、失败和未知付款、跨期补账；同时向拟合作个人与单位核对候选周期，仅记录有来源的反馈，不代发消息或签约。
- **Success Metric：**逐笔账、账单、支付和银行余额一致；重复支付及重复预留为零；基准资金情景到期缺口为零；实际合作条款能支持所用周期。
- **Failure Threshold：**任一重复支付、漏付／无依据延付或缺口出现即停止推进真实付款；未取得条款证据时周期保持待确认，不能标通过。
- **Time Limit：**账本验证两天；合作反馈未取得则明确未验证，不用模拟替代真实接受度。
- **Decision After Test：**通过后进入 P05/F03/F05 实现；失败先改账期、数据或垫资安排。本轮仅文档，所有新增场景 NOT_RUN。

新增功能验证场景（NOT_RUN）：两个客户不同账期互不影响；同主体多个账号不重复出账；同主体应收应付不混用；短月与节假日；规则生效跨期无重复遗漏；重启补建提醒；未核验付款暂缓催收；部分到账仅催余款；已结清关闭任务；已读不自动结案；发送失败可恢复；越权修改和发送被拒绝。以上仅补充测试设计，不代表本轮已实现。

## 7 柬埔寨资金服务边界核查

官方贸易资料库收录的 NBC 2017 年支付服务机构规则涉及支付服务许可及电子货币资金用途限制。该页面英文标为非正式译文，部分文字 OCR 不完整；它不证明普通物流企业的每种运费预收都需要支付牌照，也不足以确认所有现行修订。参见[官方收录原文，Articles 1、3、5、8](https://cambodiantr.gov.kh/en/document/?title=prakas-on-the-management-of-payment-service-institution)。

实际启用前按合同、账户和收付款路径核实适用规则；若实质为替第三方收付或储值支付，需由当地专业人员及合作银行／持牌服务方确认。不得把本草案当成法律认定；也不把普通内部分类账称作已依法设立的信托／托管账户。

## 8 银行托管方向记录（2026-10-24）

**来源与状态：**用户明确“合规是底线”，提出可找银行托管资金池，随后要求“先记录”。据此记录“优先评估银行托管＋DR 订单分账与结算管理”为候选方向；本次仅保存讨论，不代表银行选型、签约、开户、资金划转、开发接入或具体法律适用已批准。

拟议流程：客户付款进入协议约定的托管账户 → DR 逐笔记录订单及资金归属 → 按履约条件与各主体账期生成账单 → 财务审核 → 银行按协议释放资金 → 根据银行结果核销和对账。DR 管理业务账及结算指令，不能仅凭本地状态宣称银行已付款。平台服务费满足约定条件后转入运营账户；合作方应付、保险和退款分别管理，不自动混用或抵销。

**已核实的公开事实：**本次讨论查阅的 [BRED Bank Cambodia 官方 Escrow 介绍](https://bredcambodia.com.kh/business-banking/escrow/)说明其提供独立托管服务并持有柬埔寨 Trust Regulator 许可；公开场景主要为大额交易。[Canadia Bank 官方介绍](https://www.canadiabank.com.kh/escrow-service)也说明持牌 Escrow 服务，但主要面向房地产。这些事实证明存在银行托管产品，不证明上述银行已支持 DR 的高频小额配送结算。

**仍需书面确认：**配送平台业务是否在银行支持范围内；多付款方、多受益方与不同账期；分账、部分退款、争议冻结及放款条件；费用、最低金额、付款时效、对账文件或接口；资金权属、收益归属及平台与银行各自的资质和责任。托管不自动赋予平台使用本金或获得利息的权利；前述官方收录规则第16条的资金保护和收益归属要求是否适用，应结合实际模式确认。

**后续验证建议，尚未启动：**用一张资金流图和正常结算、部分退款、争议冻结三个样例向候选银行核对支持范围、报价与责任边界；建议一周完成首轮核对，未取得答复则保持待确认。若费用或时效不适合配送，再评估持牌支付机构的收款与结算方案。未授权代发询价、联系银行或开展真实资金试点。

本记录保持 v0.1；未修改正式 PRD、规则与验收编号，不阻塞当前基础配送闭环。银行托管及分账功能未实现、未验证，不能在 Demo 或对外材料标为已接通。

## 9 本轮 Demo 实现及后续边界

已实现：财务工作席“结算与提醒”，分待办／规则／账单／发送记录；客户、单位、个人分别配置日／周／月／每 N 天／逐单规则、生效日、出账延迟、到期天数、提前提醒、逾期跟进间隔、负责人及演示接收人。编辑时预览三个周期，短月明确按月末或顺延至有效月份，规则留版本，已绑定账项和已出账记录不静默改期。

闭环：页面检查生成草稿和持久待办 → 财务核对确认 → 模拟发送账单 → 到期收款／逾期催收 → 原订单部分到账核验或暂缓催收 → 剩余金额跟进 → 全额核销关闭待办。已读与完成分离；发送失败保留并可重试，提交前复核源账项版本和金额。已确认账单后补入的明细生成补充账单。合作应付和司机收入引用既有数据，付款链接回原合作应付／提现入口，既有付款结果用于更新提醒，不新增第二套可支付余额。

提醒在页面加载及可见财务页面每分钟检查；模拟日期可向前推进，重复检查不重复出账，重新打开页面可补查。**关闭浏览器后没有后台定时服务，也没有真实短信、邮件或银行操作。**不把模拟发送称为已通知真实客户。

原型限制：USD、日历日和金边日期；没有银行节假日接入、客户月结准入主链、正式税务开票、任务领取转派/升级通知或银行托管。旧订单缺客户主数据 ID，Demo 暂按客户名称归集，正式接入必须使用合同主体 ID。转账部分核验回写原订单，旧核验入口禁止覆盖已记录分笔收款；现金继续走原核验/交款链。司机提现付款在既有钱包核对，提醒中已支付收益按收入顺序分配仅为展示，不作为正式逐单付款分配凭证。

本轮验证仅对应[结算交互契约](../../prototype/SETTLEMENT-CONTRACT.md)及记录中的用例；生产调度、服务端隔离/事务、银行工作日日历与真实通知仍待验证，原正式 AT 不改为 PASS。

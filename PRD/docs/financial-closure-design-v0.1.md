版本：v0.1 草案，2026-10-24。依据用户本轮财务方案、V1.4 评审稿及已确认的预付／月结、保险独立记账、司机提现和按主体账期需求。本文是需求与设计增补，不是功能验收报告；不改正式 PRD 正文、RULE 或 AT 编号。与既有草案的差异在本页明确记录，待下一版整合冻结。

> 最新状态：新版跨端 Demo 已实现部分资金闭环，见[跨端需求及报表](cross-end-finance-and-reports-v0.1.md)与本文第 11 节。第 2 节旧实现描述、第 8 节 NOT_RUN 和第 9 节源码缺口保留作实现前基线，当前验证状态以本轮记录为准。

## 1 范围与必须统一的口径

核心闭环：费用依据 → 应收／应付 → 收付款申报 → 资金确认 → 对账 → 核销分配 → 未结／差异处理 → 关账与导出。收付款、对账、核销、结算、会计记账分别记录，不能用一个“已完成”代替。

- 保留“发货人先付款，再派单；获批月结例外”。账期设置不授予信用资格；付款截图不等于核验通过。运费已预付时，司机不能重复收运费。
- 已确认的司机劳动收入提现继续保留，申请 → 财务审核 → 人工付款执行登记 → 独立核验 → 核销。不做的是充值、转账类储值钱包；不能据此删除已授权的提现需求。
- 保险费独立记录金额、受益方、收付与退款状态，不参与配送费分成，也不当作 COD。配送费、保险费和货款可以一次收取，但必须有逐项分配。
- COD 已按最新用户授权纳入首期需求与新版合成 Demo。已确认代收、商户应付、返款审核及核销可演示；真实业务未启用。此决定替代此前“首期待确认”，并明确是范围增补。
- 首期基础工作先覆盖运费、合作运力、司机现金交款和已授权收入提现；自动划款、自动退款、完整总账、工资、资产、税务申报、跨公司资金池不纳入此次实现。会计接口保留导出和凭证引用。
- 银行托管仍为[已记录候选方向](partner-settlement-and-funds-v0.1.md#8-银行托管方向记录2026-10-24)，本文不构成开户、签约、银行接入或资金使用授权。

## 3 四类业务账与资金用途

1. **客户费用账**：原费用＋批准调整＝有效应收；有效应收－有效核销＝未结。银行已确认但尚未分配的钱单独展示，不自动减少某个客户或订单的欠款。多收进入有归属的待分配款／预收款；归属未知则挂待认领，不能自动当收入。
2. **合作运力应付账**：委托／指派 → 履约与协议费用核对 → 应付 → 对账 → 审批 → 付款 → 核销。客户售价不是承运商成本；接单不是最终可支付条件。客户退款也不自动扣司机收入。
3. **COD 商户往来账**：应代收与实收分开；实收确认后形成对应商户待返还义务。记录货款受益方、币种、资金保管方、已返与未返；未收到的货款不冒充已保管。货款、运费、应付默认不抵扣；合同允许时仍保留双方毛额及批准抵扣明细。
4. **司机资金保管账**：客户现金交司机形成保管事实；司机交公司是内部保管转移，不是第二笔客户收款。银行直接收款不进入司机待交现金。交接申报与公司实际点收不同，差额保留责任和证据。

四类账是业务视图，不是只有四种资金用途。保险款需独立用途和受益方；会计确认收入、税额与利润按批准政策处理，不能直接用客户实收或余额差当营业收入。

## 4 三层对账与核销分配

| 层次 | 核对对象 | 成立条件 |
|---|---|---|
| 业务对账 | 订单、交付、退回、费用、协议及批准版本 | 有依据、无漏计／重计、应收与应付独立 |
| 资金对账 | 收付款记录、银行流水、渠道结果、现金点收 | 账户、方向、币种、金额、唯一交易身份、结果及证据匹配 |
| 结算对账 | 批次、逐笔交易、手续费、退款及银行净额 | 每项可展开，毛额与净额差有独立依据，余额守恒 |

“核销”是把已确认资金分配到应收／应付并减少未结余额，不删除记录。银行交易只入账一次，但可分配多次：一笔 USD 100 的已确认收款可分配订单 A 60、B 30，剩余待分配 10；B 欠款另由另一笔收款补足。每笔分配有来源资金、目标账项、金额、币种、主体和审计引用。

AT-38 的防重复意图保留；现有“交易号只能绑定一个 collection_verification”不能直接实现一款多单。正式整合须复核原验收措辞，先将唯一性放在**银行资金事实**，再用多个核销分配及总额约束阻止重复使用，不能仅放松唯一索引。

约束：同公司、同币种、合法付款／受益主体；有效分配总额不超过确认可用款，目标分配不超过有效未结；退款、预留、冲正共同占用来源可用额。多付款主体需要授权关系，不因同一企业便可互相核销。并发在事务中锁定来源及目标余额。

撤销核销追加反向分配，恢复可分配余额；不撤销真实到账。原资金事实错误时另行冲正或标记争议，必须先处理下游分配；不允许直接删除原款。撤销导致欠款恢复时，按原合同到期日重新生成相应待办，不能重置账龄。

## 5 独立状态与误操作控制

| 维度 | 目标状态／展示 | 不能推导的结论 |
|---|---|---|
| 履约 | 待取、配送、实收、退回、异常结案 | 签收不等于结清 |
| 收款证据 | 申报待核、确认、拒绝、差异 | 截图不等于到账 |
| 应收核销 | 未核销、部分、全额；另列退款／争议 | 正常部分收款不是金额差错 |
| 司机保管 | 无需交、待交、部分点收、已点收、有差额 | 点收不增加客户收款 |
| 付款审批 | 草稿、待审、通过、驳回、取消 | 通过不等于已付 |
| 付款执行 | 未执行、执行中、结果未知、失败、确认成功 | 超时不等于失败，未知不再次付款 |
| 银行核对 | 待核、匹配、差异 | 执行成功不代表账项已分配 |
| 应付核销 | 未核销、部分、全额 | 部分付不变全额结清 |
| 通知 | 待发送、模拟／实际发送、失败；独立已读 | 已读不关闭业务任务 |

付款登记只记录执行及凭证，独立核验后形成确认资金事实，再核销。未知保留付款预留，查询原指令；确认失败后按批准重试策略复用业务身份新增执行尝试，禁止改幂等键当作新付款。出款账户变更、受益账户变更或审批金额改变须重新复核并作废旧确认版本。

批准人不能批准自己的申请或差额减免；付款执行人与资金核验人分离，按实际 actor_id 检查，不仅检查角色名称。表单展示币种、对象、应付、已付、本次金额、余款及脱敏账户；最终提交重验版本和余额。返回、筛选、详情、已读均不产生资金动作。

## 6 数据与接口目标

以下为候选逻辑实体，待 D24 与正式迁移确定，不代表已建表：

| 对象 | 最少信息与约束 |
|---|---|
| 费用／应收／应付明细 | 公司、合同主体、业务来源、用途、币种、金额、批准调整、归属期及到期日 |
| 资金交易与银行流水 | 方向、账户、渠道、交易身份、金额、币种、发生／记账日、确认方式、证据；唯一身份按渠道交易号实际作用域定义 |
| 对账匹配 | 一组业务资金与银行记录，毛额、手续费、退款、净额差及批准依据；禁止重复覆盖同一金额 |
| 核销分配 | 来源资金、目标明细、金额、幂等业务键、核销／反向分配引用 |
| 付款指令与执行尝试 | 审批版本、账户快照、有效预留、尝试号、结果、查询记录；未知不释放占用 |
| 结算单与批次明细 | 原账项引用及快照、争议范围、每次付款／分配；不创建第二套应付 |
| 现金保管与交接 | 来源收款、交出／接收方、币种、申报、点收、差额；同一现金不双计 |
| 关账与导出 | 期间、锁定人、版本、导出批次及会计映射；跨期调整引用原记录 |

所有金额用确定的整数最小单位或数据库精确数值，币种决定精度和舍入规则。USD 与 KHR 不隐式相抵，换汇显式保存两币金额、汇率、来源、时间及差额。各表复合公司外键／服务端权限；确认记录只追加更正，审计留原因和操作者，证据使用授权引用，日志不存完整银行卡／证件号。

候选动作：收款申报／核验、流水导入／去重、匹配确认／差异、核销／撤销核销、交款申报／点收、结算单确认、付款申请／批准／执行登记／结果查询／独立核验、调整批准、期间关闭、会计导出。写动作沿用幂等键与对象版本，批量核销在一个事务内验证全部来源和目标，不得只成功一半却返回整体成功。

回调应验签并按事件身份去重，乱序不能倒退已确认状态；事件去重不替代交易去重。无银行接口时用“人工核验”并记录核验人和证据，不显示自动核验。旧 Demo 已付记录缺银行证据时标待复核，不能自动升级成正式已核验，也不能因此重发款。

## 7 页面与每日五个问题

沿用现有品牌、表单、返回和分页规范，分为六个菜单，详情保留筛选，不新增长瀑布流：

| 菜单 | 页签与下一动作 |
|---|---|
| 客户应收 | 未结／月结账单／账龄；展开费用与核销，处理到期催收 |
| 收款与核销 | 待核／已确认待分配／匹配差异／历史；一笔款选择多账项并预览余款 |
| 司机交款 | 待交／点收／差额；展开原始现金来源，允许部分点收 |
| 应付与结算 | 合作运力／司机提现／付款批次；逐步审核、登记、核验和分配；COD 启用后单独商户页签 |
| 差异与更正 | 待处理／争议／退款／冲正；原记录与更正链并排查看 |
| 规则与报表 | 主体账期／待办通知／日月结／会计导出；保留现有提醒能力 |

财务首页按币种回答：客户欠多少、我们欠多少、司机持有多少、代商户保管多少、多少账款不符。未确认、已确认未分配、争议、逾期分别显示；COD 未启用显示“未启用”，不伪造零负债。托管或银行余额必须带来源与核验时间，不把预测应收显示为现金。

## 8 示例与验收输入

用户示例按 USD、无保险／税费／手续费，且运费未预付、允许交付收款的已批准例外计算；不是取消先付款守卫。

| 步骤 | 账务结果 |
|---|---|
| 费用 | 运费应收 20；COD 应代收 200；承运费按协议核对后应付 14 |
| 客户交现金 220 并完成核验 | 运费收款 20、COD 实收 200；司机持有 220；不能把 220 全记运输收入 |
| 司机交公司并点收 220 | 司机待交减少 220，公司保管增加 220；客户收款不再增加 |
| 商户返款 200，承运款 14 均确认并核销 | COD 未返 0，承运应付未结 0；仍可追踪两笔出款 |
| 业务差额 | 20 − 14 = 6，只是运输业务差额，不是净利润 |

如果运费 20 已由发货人预付，司机只收 COD 200，公司原预收 20＋司机交款 200＝合计收款 220；不得再向收货人收 20。COD 关闭时两种含 COD 场景均不可执行。

待实现验收（全部 **NOT_RUN**，不是新 AT）：一款多单／一单多款；部分付款无差错；超额待分配；跨公司／币种／主体拒绝；并发及重放不超配；撤销核销不删除资金；现金交公司不二次收款；银行直收不增加司机待交；付款登记不结清；未知不重付；审批人自批拒绝；账户变更阻断旧审批；保费不分成；结算净额含手续费；差额不抹平；锁期后补差不改历史；提醒只催未结且可催部分；旧已付记录迁移不重付。COD 启用后再跑代收、部分交款、商户返还及争议场景。

## 12 车辆责任与提现资格规则（2026-10-26）

- 自营车辆必须指定一名责任人，并绑定已核验司机；责任人负责档案、资格与异常升级，不替代司机的实际履约责任。
- 社会车辆必须指定联系人和联系电话，且仅能在合作方完成准入、协议及能力核验后，经合作运力流程派单；不得把社会车辆写入自营车队后直接派单。
- 司机提现资格由同一企业、同一币种的生效规则判断：时间周期仅可为 7、14 或 30 天；余额门槛比较当前可提现余额；管理员选择 `AND`（两项均满足）或 `OR`（任一项满足）。
- 周期从最近一次**已付款**提现起算；没有已付款提现时，从规则生效时起算。已提交、审核中、付款结果未知的申请不重置周期，仍占用余额。
- 余额门槛不是单次最低提现额；若要增加单次申请下限，须另立规则、明确币种和生效版本，不能从“可提现余额 ≥ 门槛”推导出来。
- 规则修改必须生成新版本并留存旧申请使用的资格判定快照；生产服务端在创建申请的事务内重新计算，不以客户端按钮是否禁用作为控制。

原型现已展示上述规则及 `AND`／`OR` 判断，并使用 USD 合成数据；正式版本须按企业＋币种持久化、加 RLS、版本快照与并发测试后才可宣称完成。

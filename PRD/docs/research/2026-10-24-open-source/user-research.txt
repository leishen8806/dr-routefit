# 货拉拉式调度系统＋顺路拼单配送：GitHub 开源项目调研

初步结论：值得做，而且非常适合 DR 仓配体系。但不建议直接寻找一个“货拉拉克隆版”作为整个系统。

从目前查到的 GitHub 项目看，更可行的方案是把它拆成两个核心能力：

- \*\*智能调度（Dispatch）：\*\*订单进入系统后，选择合适的司机、车辆、配送时间和路线。
- \*\*顺路拼单（Crowdshipping / Backhaul Matching）：\*\*车辆已有既定行程时，判断能否在不影响原订单的前提下，顺路承接其他包裹。

这两者的底层算法有所重叠，但业务规则不同：调度关注整个运力池，顺路拼单关注现有路线能不能以较小的额外成本插入新订单。

## 四、“顺风车带快递”的核心不是最近司机，而是最小增量成本

假设一辆货车已经有原始路线：

示意图，非真实地图和路线测算。

系统收到一笔新快递订单，取件点为 P，交付点为 D。

算法应计算：

\\[ \Delta T=T\_{\text{插单后}}-T\_{\text{原路线}} \\]

同时计算新增里程、费用及原有订单的延误风险。

建议将下面这些条件设为硬约束：

| 约束    | 建议规则                            |
| ----- | ------------------------------- |
| 先取后送  | P 必须先于 D                        |
| 载重与体积 | 全程不得超过车辆剩余容量                    |
| 原订单承诺 | 不得突破已经承诺的送达时间窗                  |
| 额外绕行  | 初期可测试不超过 15 分钟或原路线时间的 15%，取较严格值 |
| 新件时效  | 必须在新订单要求的窗口送达                   |
| 货物适配  | 不相容、易损或需要特殊运输的货物不得错误混装          |
| 司机确认  | 初期只推荐，不自动强制接单                   |
| 交付凭证  | 每个包裹独立扫码、签收和异常记录                |

上表的 15 分钟、15% 是建议试验参数，不是货拉拉的公开规则，也不是算法研究证明的最优值。

VROOM 与 OR-Tools 都能够处理取送货和时间窗等基础约束，但“司机愿不愿接”“新增收入是否覆盖成本”“货物是否适合混装”仍需要在 DR 自己的业务规则层判断。

## 五、DR 仓配系统如何落地

结合目前的 W1、W2、W3 规划，建议不要把整套开源物流系统直接塞进现有 Three.js 仓配场景。应当区分运营后台、调度计算和三维展示。

DR 调度控制台

订单、车辆、司机、运单、分配、异常与签收

调度服务

Fleet-Ops / OwnFleet 机制对标

顺路拼单服务

插单可行性、报价与收益计算

VROOM / OR-Tools

路径与容量优化

OSRM / 路网服务

ETA 与行驶时间矩阵

DR 三维园区与全景大屏

只读展示 W1/W2/W3 运单流向、车辆、状态与异常

这样能保留现有项目的工程边界：三维场景是可视化层，不直接决定真实派车、签收或运单完成。

### 顺路配送的业务闭环

建议流程为：

`新订单 → 查找已规划路线 → 筛选顺路车辆 → 插入取送货点 → 校验容量与时效 → 计算司机补偿 → 司机确认 → 生成配送任务 → 扫码取货 → 运输跟踪 → 签收`

有几个边界需要优先设计：一笔运单不能被两个司机并发领取；车辆临时改线要重新验证所有原订单的送达窗口；包裹丢失或超时必须有明确责任与异常处理记录。若未来开放社会司机，还需另行核查当地货运经营、保险、承运责任、个人数据和司机资格等要求。

## 六、建议的实施路线

| 阶段          | 工作范围                                                        | 验收目标                  |
| ----------- | ----------------------------------------------------------- | --------------------- |
| R0：开源技术尽调   | 深入阅读 Fleetbase、OwnFleet、VROOM、OR-Tools、OSRM 的源码、许可证、依赖和更新状态 | 确定复用与自研边界，不修改现有业务系统   |
| R1：基础调度 MVP | 订单池、司机车辆、人工派单、推荐派单、轨迹与签收                                    | 能用测试订单完成一条配送闭环        |
| R2：顺路拼单 MVP | 固定路线中插入新取送点，计算绕行与补偿                                         | 能拒绝超时、超载和不经济的插单       |
| R3：动态调度     | 行驶中新增订单、司机拒单、异常改派、订单优先级                                     | 原订单 SLA 不因算法调度遭到无提示破坏 |
| R4：DR 三维联动  | 把已验证的调度摘要展示在 W1/W2/W3 园区与仪表盘                                | 三维状态与业务记录一致，无额外业务写入   |

先在模拟订单和受控车队上验证 R1、R2，比直接开放社会司机接单更合适。

对于顺路拼单，建议首轮实验记录四项结果：匹配成功率、每单增加的绕行时间、原订单准时率、每单平均配送成本。只有这些指标一起改善，才说明算法具备实际商业价值。

## 七、最终开源选型建议

业务平台对标：Fleetbase / Fleet-Ops

功能最完整，尤其适合分析调度、车队、订单执行与司机 App。不过 AGPL 和整体技术栈需要单独评估，不建议直接替换 DR 现有后台。

路线优化主候选：VROOM

先用于批量订单和顺路插单可行性测试；OR-Tools 作为复杂约束求解的备选或对照基线。

地图与路网：OSRM

适合形成自有道路时间矩阵，但需检查金边本地道路数据质量；路线优化不能只靠经纬度直线距离。

顺路匹配算法研究：Crowdshipping 项目

重点参考其匹配与补偿模型，暂不把神经网络动态定价作为 MVP 必需功能。该仓库还依赖 IBM CPLEX，部署和授权成本需要评估。

# RF-PM-055 · RouteFit 正式登录与会话设计

状态：**设计草稿，待负责人批准；未写实现**

基线：`develop` `bd848893dd88018cdb332e6686c1eb39dba5b818`

范围：员工网页、司机 iOS／Android App、Telegram Mini App 的正式身份与会话，以及从受控试运营链路迁移的方式。

## 0. 决策边界

### 0.1 已确认事实

- 当前服务拒绝 `NODE_ENV=production` 和非 `development` 的认证模式，只监听本机回环地址。
- 员工通过 SSH 隧道领取 60 秒一次性链接；浏览器会话来自 root 专用的 `sessions.json`。
- 当前浏览器会话使用 `HttpOnly`、`SameSite=Strict` Cookie，非 GET 请求还校验精确 Origin 与 CSRF；这只属于本机开发契约，不是正式身份系统。
- `org.principal` 是内部主体，权限来自可信会话；客户范围还必须由 `party.customer_access` 等资源授权校验，客户端不得决定企业范围。
- Telegram `initDataUnsafe`、用户名和客户端提交的客户 ID 都不可信；服务端必须验证原始 `initData`。
- 司机设备可能遗失或离线，必须能按设备撤销，不得把“登录成功”等同于“可访问所有任务”。

### 0.2 设计假设

- 首期只有一个正式 Web 域名，但认证模型不得依赖单企业或单客户端。
- 员工数量较少，仍需要可审计的入离职、禁用和强制登出；不能以共享账号替代身份治理。
- 驾驶员 App 能使用系统浏览器和系统安全存储；不能保证所有设备都支持硬件证明。
- Telegram Mini App 仅提供客户入口；Telegram 身份必须先绑定到企业内的受邀客户成员，不能自动创建业务授权。

### 0.3 未知项

- 身份提供方、短信和邮件服务商及其数据驻留、SLA、价格与柬埔寨号码覆盖；
- 正式域名、告警接收渠道、值班人和证书管理责任人；
- 员工是否强制 MFA、司机是否允许短信 OTP 作为恢复方式；
- Telegram 客户绑定的人工核验流程与账号恢复规则；
- 正式登录上线时的维护窗口和旧试运营会话是否允许回滚恢复。

### 0.4 最强反对理由

1. **外部身份依赖尚未决定。** 先写死某一家会造成账号迁移、数据驻留和持续费用锁定。
2. **一次同时覆盖三类主体，爆炸半径大。** 员工、司机和 Telegram 的信任来源不同，共用一个“万能登录接口”会把弱认证提升为高权限会话。
3. **从文件会话直接迁移令牌风险过高。** 旧 token 与 CSRF 哈希缺少正式会话的设备、撤销族和认证上下文；导入会制造无法解释的正式登录。

### 0.5 最强支持理由

1. 现有 `principal`、权限和客户授权已经把“身份”与“业务授权”分离，正式认证可以只替换身份与会话入口。
2. 采用标准 OIDC／PKCE 和服务端 Telegram 校验，可避免自建密码库，并让员工、司机、客户保持独立信任链。
3. 分批上线、默认拒绝和旧开发入口不暴露公网，可把高风险切换做成可回滚的维护窗口。

### Verdict

采用“**统一内部主体与授权，分离三类认证入口**”的架构：员工使用 OIDC＋服务端 Web 会话；司机使用 OIDC Authorization Code＋PKCE、短访问令牌和按设备轮换的刷新令牌；Telegram 由服务端验证原始 `initData`，再换取受限客户会话。不得迁移旧 token，只复用经核对的主体标识与业务授权。

### Confidence

**84%**。标准协议和现有授权边界使方向可信；置信度主要受身份提供方、账号恢复和真实设备能力尚未决定影响。

### Why

它在不重写业务权限模型的前提下关闭共享账号、明文令牌和本地文件会话的生产风险，并为司机与 Telegram 提供互不越权的正式入口。

### Key Variables

1. 身份提供方能否满足 MFA、账号生命周期、审计和区域可用性；
2. 现有主体与正式外部 subject 的一对一绑定质量；
3. 移动端安全存储、刷新令牌轮换和远程撤销的真实设备表现。

### Largest Unknown

正式身份提供方与账号恢复流程尚未决定；这是实施成本、上线时间和安全责任最大的变量。

### Reversal Condition

若候选身份提供方无法满足 MFA、主体唯一性、审计导出和可接受的数据驻留，员工方案改为经独立安全评审的自托管 OIDC；不退回自建密码表或共享账号。

### 最小验证实验

- **Hypothesis：** 一个候选 OIDC 提供方能把既有 5 个合成主体一对一绑定，在禁用用户后 60 秒内阻断新会话，且不改变业务权限。
- **Test：** 在独立环境用合成主体完成登录、MFA、禁用、重新登录和跨企业负例；同时在一台 iOS、一台 Android 验证 PKCE 与安全存储。
- **Success Metric：** 主体无重复；禁用阻断 ≤60 秒；跨企业请求 404；日志无令牌；两台真机均能登录、轮换和撤销。
- **Failure Threshold：** 任一重复主体、跨企业可见、令牌进入日志，或禁用后仍可建立新会话。
- **Time Limit：** 2 个工作日的技术试验，不接真实数据。
- **Decision After Test：** 全部通过才批准身份提供方适配批次；否则更换提供方或进入自托管 OIDC 评审。

## 1. 总体架构与不变量

```text
员工浏览器 ── OIDC ──┐
司机 App ── OIDC/PKCE ├─> Auth Adapter ─> Formal Session Store ─> RouteFit API
Telegram Mini App ────┘                         │
                                                └─> principal + permissions + resource grants
```

不变量：

1. 外部身份只证明“是谁”，不直接授予企业、角色、客户或订单范围；
2. 每个请求从已验证会话取得 `principalId` 和企业，绝不信任客户端提交的企业 ID；
3. 主体必须 `ACTIVE`，角色／权限有效，资源还要通过客户授权、司机分配或其他对象级校验；
4. 跨企业资源仍按契约返回 404，避免确认资源存在；
5. 数据库只保存会话或刷新令牌的不可逆摘要；原始令牌只在签发时返回一次；
6. 认证适配器与业务授权分层，不能由登录入口绕过 RLS 或对象授权；
7. 开发认证与正式认证互斥；正式进程不注册 `/dev/*` 路由，也不读取 `sessions.json`。

## 2. 三类主体的登录方案

### 2.1 员工网页

| 方案 | 安全性 | 实现量 | 外部依赖 | 结论 |
| --- | --- | --- | --- | --- |
| A. 托管 OIDC，Authorization Code＋PKCE，BFF 建立服务端 Cookie 会话 | 高：可用 MFA、禁用、异常登录策略；RouteFit 不保存密码 | 中 | OIDC 身份提供方；邮件或手机号由提供方负责 | **推荐** |
| B. 自托管 OIDC（例如独立身份服务），同样由 BFF 换会话 | 高，但补丁、可用性、备份和恢复由团队负责 | 高 | 自有运维；邮件／短信仍可能需要外部服务 | 候选提供方不合格时的备选 |
| C. RouteFit 自建账号密码／邮件魔法链接 | 中到低：需承担密码、恢复、反枚举和邮件投递风险 | 很高 | 邮件或短信；安全运维 | 不选 |

推荐 A。RouteFit 只接收 OIDC `issuer`、`subject`、授权码流程结果；以 `(issuer, subject)` 绑定一个内部 STAFF principal。邮箱和显示名只能作展示／联系字段，不能作稳定主键。首次绑定必须由预先批准的员工登记完成，不能因 OIDC 登录自动创建员工或角色。

### 2.2 司机 iOS／Android App

当地司机可能只有手机号，没有稳定邮箱或可复用的第三方账号。司机 principal 必须先由批准的司机名册／入职流程建立；任何登录方案都不得仅凭一个新手机号自动创建主体、企业或任务权限。

| 方案 | 开户方式 | 安全性 | 成本与实现量 | 外部依赖／主要风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 系统浏览器 OIDC Authorization Code＋PKCE | 运营预登记司机；身份提供方创建账号，可使用其支持的手机号登录而不强制邮箱 | 高：不把密码交给 App；可统一 MFA、禁用和审计 | 中到高；按身份提供方计费，RouteFit 只实现标准协议与主体绑定 | OIDC 提供方、App Universal Link／App Link；需核实柬埔寨手机号覆盖和无邮箱开户 | **推荐首选** |
| B. 手机号＋短信 OTP，由 RouteFit 签发设备会话 | 运营预登记并核对手机号；首次及重新认证时验证 OTP，再绑定既有 DRIVER principal | 中：可覆盖无邮箱司机，但短信不是抗钓鱼因子 | 高；短信单价、投递、限速、反枚举、恢复和客服均由 RouteFit 承担 | 短信服务商；SIM 换卡、号码回收、短信劫持与投递失败 | **首期正式候选，不只用于恢复** |
| C. 长期 API Key／员工代发静态令牌 | 人工发放共享或长期凭据 | 低：难轮换、易复制、无法证明设备 | 低 | 无；但撤销、归责和设备丢失风险不可接受 | 禁止 |

推荐 A，前提是候选 OIDC 提供方在批次 0 证明“手机号开户、无邮箱、柬埔寨号码投递、账号禁用和审计导出”都可用；它仍通过系统浏览器 PKCE 建立设备会话。若该前提失败，B 是正式首期候选而非恢复手段，但必须保持“预登记主体＋OTP 只证明手机号控制权＋服务端业务授权”的边界，并接受 SIM 换卡／号码回收的残余风险。最终选择属于阻塞批次 0 的负责人决定。

司机设备会话分两期：

- **首期（批次 5）：** 系统浏览器 PKCE（选择 A 时；选择 B 时由 OTP 认证入口完成等价会话交换）、10 分钟短访问令牌、刷新令牌逐次轮换与重用检测、服务端设备记录及按设备撤销。令牌只存系统安全存储，不要求设备私钥签名。
- **后续独立高风险批次：** 设备私钥签名的持有证明、挑战防重放与硬件保证级别；根据设备能力限制高风险动作。

首期不做设备签名时，攻击者一旦同时复制刷新令牌和可伪造的设备标识，可能在重用检测触发前冒充设备。缓解措施是短访问令牌、一次性刷新轮换、并发／旧令牌重用即撤销整族、服务端按设备紧急撤销、系统安全存储、TLS、禁止令牌进日志，以及敏感动作重新认证；这仍是需要负责人接受的残余风险。

### 2.3 Telegram Mini App 客户

| 方案 | 安全性 | 实现量 | 外部依赖 | 结论 |
| --- | --- | --- | --- | --- |
| A. 每次进入时把原始 `initData` 交给 RouteFit 服务端验证，绑定受邀成员后换取短期 HttpOnly 客户会话 | 高：Bot token 不下发；业务授权仍由内部成员与客户范围决定 | 中 | Telegram Bot／Mini App；HTTPS | **推荐** |
| B. 每个 API 请求都携带并重新验证原始 `initData` | 中：减少自有会话，但扩大敏感材料传播和日志泄漏面，撤销与 CSRF 语义更差 | 中 | Telegram | 不选 |
| C. Telegram 后再跳第三方 OIDC 登录 | 高但摩擦大；失去 Telegram 入口的主要价值 | 高 | Telegram＋OIDC | 仅用于高风险操作的二次认证候选 |

推荐 A。服务端按 Telegram 规范使用 Bot token 派生密钥验证原始 `initData` 的签名，校验 `auth_date` 新鲜度和必需字段，并把 `(botId, telegramUserId)` 映射到已受邀、状态有效的客户成员／principal。`username`、显示名和客户端 customerId 不参与授权。未绑定身份只得到“待绑定”状态，不能读取客户或订单。

## 3. 会话模型

### 3.1 统一数据对象

正式会话建议使用数据库持久化，逻辑对象分为：

- `auth_identity`：外部 issuer／provider、external subject、绑定 principal、状态和验证时间；
- `auth_session`：会话 ID 摘要、principal、认证方式、认证时间、最近活动、绝对到期、撤销时间、风险上下文；
- `auth_refresh_family`：移动端设备、当前刷新令牌摘要、轮换序号、绝对到期、撤销与重用时间；
- `auth_device`：principal、平台、设备公钥、保证级别、最后使用、撤销状态；
- `auth_audit_event`：只追加的登录、失败、刷新、撤销、绑定与敏感动作事件。

字段名和迁移由后续契约／数据模型批次批准；本设计不创建表。

### 3.2 员工网页会话

- Cookie：建议名为 `__Host-routefit_session`，`Secure`、`HttpOnly`、`Path=/`、无 `Domain`；OIDC 回调需要顶层导航，首期使用 `SameSite=Lax`。
- CSRF：登录后生成独立随机 CSRF secret；非安全方法要求精确 Origin／Host 与 `X-CSRF-Token` 双重提交。CSRF 不放 URL。
- 有效期：空闲 30 分钟；绝对 12 小时；距绝对到期不足 30 分钟时不静默跨越上限，要求重新 OIDC 登录。
- 高风险动作：角色变更、设备撤销、身份绑定和管理员操作要求最近 15 分钟内重新认证或 MFA；具体清单由负责人批准。
- 轮换：登录成功和权限提升时更换会话 ID；旧 ID 立即撤销，防止会话固定。

### 3.3 Telegram Web 会话

- 验证成功后签发独立客户 Cookie，会话类型与员工 Cookie 分开；不能拿客户会话调用员工 API。
- 有效期：空闲 30 分钟、绝对 8 小时；到期后用新的 `initData` 重新交换。
- `initData` 接受窗口建议 5 分钟；保存其不可逆指纹至窗口结束，拒绝重复交换。
- Mini App 页面只保留必要的内存状态；不在 localStorage、日志或错误页面保存 `initData` 或会话令牌。

### 3.4 司机移动会话

- 访问令牌：不透明随机令牌，10 分钟有效；数据库只存摘要，可在撤销后立即失效。
- 刷新令牌：每次成功使用都轮换；7 天不活动失效，绝对 30 天到期；旧令牌再次出现时撤销整个设备令牌族并告警。
- 首期设备关联：服务端登记设备记录，令牌族只能归属一个设备记录并可按设备撤销；刷新令牌只存 iOS Keychain／Android Keystore 支持的安全存储。首期不把可伪造的设备 ID 当作密码学持有证明。
- 后续设备持有证明：刷新请求增加设备私钥签名，覆盖单次挑战、刷新请求 ID 和时间；服务端记录硬件保证级别，并允许策略拒绝低保证设备。
- 撤销：支持单设备、该司机全部设备、主体禁用和公司级紧急撤销；App 登出同时撤销刷新族和推送令牌。
- 离线：只缓存已授权任务和最少字段；本地加密；离线操作带幂等键和单调序列，联网后服务端重新鉴权，不以本地角色决定权限。
- 首期残余风险：刷新令牌和设备标识同时被盗时，攻击者可能在重用检测前使用令牌；以短访问令牌、逐次轮换、重用撤销整族、服务端撤销、敏感动作重新认证和日志脱敏降低风险，但设备签名批次完成前不能声称具备持有证明。

### 3.5 principal、permissions 与 access grants 映射

1. 认证完成后只能得到 `principalId`；会话不接受客户端声明的角色、permissions 或 companyId。
2. 签发时读取主体状态、角色授权和资源范围，记录授权版本／快照摘要用于审计；请求时仍校验主体未禁用、会话未撤销。
3. 员工权限由有效角色授权计算；客户授权由客户成员和 customer access 决定；司机只能访问当前分配且状态允许的任务。
4. 对撤销延迟敏感的授权不只依赖令牌内 claims。首期每次请求查服务端会话和授权；若以后缓存，最长 60 秒并带 revocation version。
5. 主体禁用、角色撤销、客户授权撤销或司机分配撤销必须使后续请求立即失败；不能等访问令牌自然到期。

## 4. 从开发会话迁移

### 4.1 原则

- **不迁移任何旧 token、CSRF secret 或其哈希。** `sessions.json` 只用于核对主体、角色和迁移清单。
- 只复用经核对的 `principal` 及现有业务授权；外部 subject 由负责人批准后绑定，禁止按显示名或邮箱自动匹配。
- 正式模式与开发模式不能同时在公网运行；切换后 `/dev/activate`、开发身份和本地一键链接全部不可达。

### 4.2 迁移步骤

1. **准备：** 导出仅含匿名主体 ID、状态和角色数量的核对清单；备份数据库与 `sessions.json`，均按现有 root-only 流程保存。
2. **预绑定：** 为每名正式员工建立待激活的外部身份绑定；双人核对 principal 与外部 subject，角色和客户授权不改。
3. **维护窗口：** 停止 RouteFit；冻结 `trial:staff`、`trial:renew` 和一次性链接签发；记录旧会话数量。
4. **作废旧链路：** 轮换或删除 trial 会话文件中的活动会话，清空未领取的一次性 grant，撤销开发 Cookie；不得把旧哈希导入正式会话表。
5. **启动正式模式：** 反向代理只转发正式路由；至少两个不同角色的合成员工完成 OIDC 登录、权限正例和负例。
6. **放行：** 全部员工重新登录；核对 principal 数、角色授权数、客户授权数与切换前一致。

### 4.3 `trial:staff` 与 `trial:renew` 的过渡

- 设计批准后的实现必须给两个脚本明确的环境门禁：正式认证启用后默认拒绝执行，不得再写正式会话。
- `trial:staff` 可保留为受控试运营／恢复环境的主体登记工具，但不能成为正式账号创建入口；正式员工生命周期由身份管理流程驱动。
- `trial:renew` 只轮换 trial 文件会话；正式会话必须通过撤销／重新认证处理。命令名和输出应明确模式，避免误操作。
- SSH `tunnel-link` 仅保留 break-glass 运维用途，不再向正式员工签发日常入口。

### 4.4 旧链接如何失效

- 未领取的一次性 grant 在切换前统一删除；已领取的开发 Cookie 因正式进程不加载 `sessions.json` 且 Cookie 名／会话存储不同而失效。
- 反向代理禁止 `/dev/*`；即使知道旧 ticket，也不能到达处理器。
- 旧 trial 会话文件继续保持 root-only，迁移证据确认后按批准的保留期销毁；不能作为正式登录的回退捷径。

### 4.5 回滚

1. 回滚触发：正式登录不可用、主体映射不一致、跨企业访问、令牌泄漏、撤销失效或审计缺失。
2. 关闭公网业务入口，保留运维 SSH；恢复上一个已批准版本与数据库备份到新库验证，不直接覆盖原库。
3. 若失败不是安全事件，负责人可决定临时恢复旧 trial 代码与维护窗口前的 `sessions.json`；若涉及令牌泄漏、主体错绑或跨企业风险，**不得恢复旧会话**，必须运行受控续期并重新领取链接。
4. 回滚后正式会话全部撤销，外部身份绑定保留为待调查状态，不自动删除审计。
5. 回滚只恢复受控 SSH 隧道员工入口；司机与 Telegram 保持关闭，直到重新批准。

## 5. 部署拓扑

```text
Internet
  └─ HTTPS reverse proxy / WAF (public 443)
       ├─ employee web + API
       ├─ driver API
       └─ Telegram Mini App + webhook
            └─ RouteFit app (loopback or private Unix socket)
                 └─ PostgreSQL (local/private only)

Restricted admin network
  └─ SSH (source restricted, key only, operations/break-glass)
```

- 一个正式主域名可按路径分员工、司机和 Telegram API；若使用子域名，Cookie 不设置共享 Domain，避免跨应用泄漏。
- 证书由反向代理自动续期，私钥只存反向代理受限目录或系统凭据存储；监控证书到期。
- 公网只开放 443；80 仅用于明确批准的 HTTP→HTTPS 跳转／ACME，若 DNS 验证可用则可关闭。数据库和应用监听不对公网开放。
- 反向代理清理客户端伪造的转发头，只从受信代理写入客户端 IP；限制请求体、超时和上传。
- SSH 隧道保留给运维和 break-glass，不作为员工正式登录；仅密钥、来源限制、无 shell／端口白名单继续生效。
- Telegram webhook 使用 HTTPS 与 Telegram `secret_token`；以 botId＋updateId 去重。Bot token 只在服务端凭据存储。

## 6. 防护与审计

### 6.1 登录限速与锁定

- 限速维度：来源 IP、规范化账号／外部 subject、设备、公司和全局；不能只靠 IP。
- 建议初值：员工同一账号 5 次失败／15 分钟后指数退避，最多锁 30 分钟；司机／Telegram 交换 10 次／5 分钟。准确值须压测和负责人批准。
- 锁定不返回“账号存在”；前台用统一错误，审计保留内部原因。
- 全局异常峰值触发告警；不能因攻击锁死全部员工，管理员必须有受审计的解锁流程。

### 6.2 审计日志

只追加记录：事件 ID、时间、认证类型、匿名 principal／device／session ID、动作、结果、原因码、目标类型／ID、公司、幂等键、受信来源 IP、设备摘要和关联 requestId。必须覆盖登录、失败、MFA、会话签发／轮换／撤销、刷新重用、身份绑定、主体禁用、敏感授权和跨企业拒绝。

### 6.3 密钥与令牌存放

- OIDC client secret、Telegram Bot token、Cookie／令牌 pepper、告警凭据放系统凭据存储或受限 secret file；生产启动前校验 owner 与权限。
- 数据库只存随机会话／刷新令牌的带 pepper 摘要；设备只存公钥。
- iOS 私钥与刷新令牌进 Keychain；Android 进 Keystore 支持的加密存储；Web 不用 localStorage 保存会话。
- 密钥有版本和轮换期；轮换支持短暂双读，过期版本按会话族撤销。

### 6.4 禁止进入日志的内容

禁止记录：密码、OTP、OIDC 授权码、ID／access／refresh token、Cookie、CSRF secret、完整 Telegram `initData`、Bot token、密钥、连接串、公钥原文、完整手机号／邮箱／姓名／地址。错误输出只含原因码、匿名 ID、计数和 requestId。

## 7. 监控与告警

| 类别 | 指标／事件 | 建议告警 |
| --- | --- | --- |
| 可用性 | 登录／回调／刷新成功率、延迟、5xx、数据库池、反向代理健康 | 5 分钟错误率或延迟超阈值 |
| 攻击 | 登录失败、锁定、无效 CSRF／Origin、无效 `initData`、重放、刷新令牌重用 | 单账号、单来源和全局峰值分级 |
| 授权 | 401／403／跨企业 404、禁用主体请求、撤销后仍访问 | 跨企业或撤销失效立即高优先级 |
| 会话 | 活动会话、签发／撤销、过期清理、刷新族、每主体设备数 | 异常增长、清理停滞、同族重用 |
| 依赖 | OIDC discovery／JWKS、Telegram API、证书、DNS、时间同步 | 不可用、JWKS 过旧、证书余期不足 |
| 审计 | 审计写入失败、队列积压、时间倒退、字段脱敏检查 | 任一写入失败阻断敏感动作并告警 |

告警至少发到一个主运维渠道和一个独立备用渠道；高优先级要求确认与升级。具体渠道、值班人、阈值和静默规则由负责人决定，不能把原始请求或令牌附在告警中。

## 8. 威胁模型

| 威胁 | 入口／后果 | 对策 | 必测负例 |
| --- | --- | --- | --- |
| 伪造 Telegram `initData` | 冒充客户、读取订单 | 服务端按 Bot token 验签；验证 `auth_date`、botId、字段；只映射受邀成员 | 改字段、错 bot、过期、缺字段均拒绝 |
| `initData` 重放 | 重复换取会话 | 5 分钟窗口；不可逆指纹单次使用；交换接口幂等并限速 | 同一原文第二次交换拒绝 |
| 访问／刷新令牌被盗 | 冒充司机或员工；首期刷新令牌与设备标识同时被复制时，重用检测前仍有冒充窗口 | 首期：短访问令牌、刷新轮换与重用撤销整族、系统安全存储、服务端按设备撤销、敏感操作重新认证；后续：设备私钥持有证明与硬件保证级别 | 旧刷新重用撤销整族；首期记录残余冒充窗口，后续拒绝无有效设备签名的刷新 |
| 跨企业访问 | 数据泄漏 | 企业来自会话；RLS＋对象授权；跨企业 404；缓存带公司与授权版本 | A 会话读取 B 资源为 404 |
| 会话固定 | 攻击者预置 session ID | 认证成功和权限提升时轮换；不接受 URL session；`__Host-` Cookie | 登录前 Cookie 登录后不可复用 |
| CSRF | 借员工浏览器执行写操作 | Secure HttpOnly SameSite Cookie；精确 Origin；独立 CSRF header | 缺 header／错 Origin 不发起业务写入 |
| OIDC 回调劫持 | 账号错绑／登录 CSRF | Authorization Code＋PKCE、state、nonce、精确 redirect URI、issuer／audience 校验 | 错 state／nonce／issuer 拒绝 |
| 主体错绑 | 外部账号取得他人权限 | 预登记＋双人核对；稳定 `(issuer, subject)`；禁止按邮箱自动合并 | 已绑定 subject 不能绑定第二主体 |
| 丢失司机设备 | 暴露任务／客户数据 | 设备撤销、最少离线缓存、本地加密、推送令牌撤销 | 撤销后刷新和 API 均失败 |
| 日志泄漏 | 长期凭据暴露 | 结构化 allowlist 日志、集中脱敏、CI secret scan、告警不附请求体 | 注入 token 后日志扫描无匹配 |
| 时钟偏差 | 接受过期断言／拒绝合法登录 | NTP 监控；有限时钟容差；服务端 UTC | 超容差 `auth_date`／JWT 拒绝 |

## 9. 测试计划

### 9.1 真实 PostgreSQL 集成测试

每次使用独立合成数据库，至少覆盖：

1. 外部 identity 一对一绑定；重复 issuer＋subject、跨企业错绑和禁用主体均拒绝；
2. 员工 OIDC 回调：state、nonce、PKCE、issuer、audience、签名、过期和 JWKS 轮换正负例；
3. 登录前后会话 ID 轮换；Cookie 标志；CSRF／Origin 正负例；登出和管理员撤销立即生效；
4. Web 空闲／绝对到期与重新认证；并发撤销无竞态；过期清理不误删活动会话；
5. Telegram `initData` 正确签名、篡改、过期、重放、错 bot、未绑定与已停用成员；
6. 司机首期：访问令牌到期、刷新轮换、并发刷新、旧刷新重用、设备记录撤销和主体禁用；后续设备证明批次再覆盖签名错误、挑战重放、密钥轮换和硬件保证级别；
7. 三类会话不能互调错误 API；客户端 companyId／role／customerId 注入无效；
8. 跨企业订单、客户、案件、司机任务返回 404；同企业无资源授权也拒绝；
9. 角色授权和客户授权撤销后，已有会话下一请求失败；授权缓存（若实现）不超过批准延迟；
10. 审计事件只追加、字段齐全、失败时敏感动作 fail closed；日志扫描无禁止内容；
11. 从 v0.3.1 形状迁移：principal／授权数量不变，旧 token 不可用，正式 subject 绑定不重复；
12. 回滚演练：恢复旧版本和备份到新库，正式会话不可被旧代码接受，旧入口只在批准条件下恢复。

| 14 | 目标日期与质量门禁冲突时是否顺延 | 后续批次前决定 | 首个生产切换窗口排期前；本设计建议不压缩身份、RLS、真机和回滚验收 |

## 12. 明确不在本设计中实施

- 不实现密码登录、短信发送、OIDC provider、Telegram Bot、司机 App、数据库迁移或正式 API；
- 不购买域名／证书／身份服务，不配置 DNS、反向代理、监控或服务器；
- 不迁移任何真实员工或客户，不生成生产密钥；
- 不改变现有 `principal`、permissions、role grants、customer access 或 RLS；
- 不把开发模式放到公网，也不把 SSH 一次性链接包装成正式登录。

# RF-PM-049 · 策略撤销／替代机制设计（v0.4.0）

状态：设计草案，待负责人侧 Claude 审查并由 `leishen8800` 批准。本文不进入 `contracts/`，不改变运行时代码或页面。

## 1. 目标、边界与术语

本设计为已发布费率策略增加可审计的“撤销（retire）”能力，同时保留已发布记录不可变的约束。撤销只影响策略是否出现在默认可选列表，不追溯修改已经生成的报价。

本文与 RF-PM-050 共用以下术语：

- **数据类别（data class）**：根记录的 `TEST` 或 `PRODUCTION` 类别；关联记录按规则继承，不能靠名称前缀推断。
- **策略（policy）**：可被报价流程读取的费率规则及其发布快照。
- **发布快照（publication）**：一次不可变的正式发布记录，拥有独立 ID、版本与有效期。
- **撤销事件（retirement event）**：追加写入的、不可变的事件，指向一个发布快照并记录原因。
- **替代关系（supersession）**：新发布快照声明替代旧快照的关系；它不等同于撤销，除非另有明确的撤销事件。

RF-PM-049 先完成设计并获批准，再拆实现卡；RF-PM-050 复用本节术语和审计边界后再开始数据分类设计。两者都属于 v0.4.0，均不得回写 v0.3.1 的实现范围。

## 2. 状态模型：发布记录不变，撤销作为事件

### 2.1 发布快照状态

发布快照本身只保留事实字段：`publicationId`、`policyId`、`version`、`dataClass`、`effectiveFrom`、`validUntil`、发布人、发布时的内容指纹。已有字段和内容不被更新或删除。

默认可选性是一个读模型，而不是对发布快照做覆盖更新：

| 读模型状态 | 判定 | 默认列表行为 |
| --- | --- | --- |
| `ACTIVE` | 已发布、在有效期内、没有生效的撤销事件 | 出现在默认策略列表 |
| `EXPIRED` | `validUntil` 已到达 | 不出现在默认列表 |
| `RETIRED` | 存在已生效撤销事件 | 不出现在默认列表 |
| `FUTURE` | `effectiveFrom` 尚未到达 | 不出现在默认列表 |

撤销事件只追加，不覆盖发布快照。若撤销事件被发现无效，应追加“撤销事件作废/更正”事件并由读模型按事件顺序计算；不得删除原事件或改写原发布记录。实现卡需要明确事件版本和并发唯一性约束。

### 2.2 已生成报价的处理

报价必须保存所用发布快照 ID、版本、内容指纹和当时的有效性证据。之后撤销策略不会使已有报价失效，也不会自动重算或替换报价。报价自身的生命周期、客户确认和财务流程仍按现有规则执行。

## 3. 替代关系：声明替代不等于撤销

新发布快照可以声明 `supersedesPublicationId`，形成从新快照指向旧快照的有向关系。关系只记录“新版本取代旧版本的业务意图”，不改变旧快照状态。

建议将“替代”和“撤销”设计为两个动作：

1. **替代**：在新发布时声明关系；旧策略仍可在有效期内被查询，除非另有撤销事件。
2. **撤销**：独立的复核后动作；只有撤销事件生效后，旧策略才从默认列表移除。

这样可表达“新策略上线但旧策略仍作为回退选项”和“发现错误、立即停用旧策略”两种不同意图，也避免发布人通过一次发布隐式改变另一条不可变记录。若负责人决定采用“一次操作同时替代并撤销”，实现卡仍须在同一事务中产生两条可审计事实，并保留独立审批主体；不能把撤销状态写回旧快照。

必须拒绝以下关系：自指、环、跨公司、跨数据类别（`TEST` 与 `PRODUCTION`）、指向不存在或已删除的 ID。历史关系保留，撤销不删除关系。

## 4. 职责分离与权限草案

撤销与发布同级但不同责。发布人不能独自撤销自己发布的策略，也不能同时完成撤销复核。

建议新增权限（名称为草案，不进入 `contracts/`）：

- `pricing:retire:request`：提交撤销申请并填写原因；可授予策略运营人员，但不能批准自己的申请。
- `pricing:retire:review`：独立复核并批准/拒绝撤销；必须是与申请人不同的自然人。
- `pricing:retire:read`：读取撤销事件和当前读模型状态；按现有策略读取范围授予。
- `pricing:supersede:declare`：在新发布中声明替代关系；建议授予发布流程角色，但仍受数据类别和公司范围约束。

建议角色映射：

| 角色 | 可做 | 不可做 |
| --- | --- | --- |
| `policy_author` | 创建草稿、提交撤销申请、声明替代 | 批准撤销；独立复核自己的申请 |
| `policy_reviewer` | 复核并批准/拒绝撤销；读取审计 | 发布、批准自己提交的撤销 |
| `policy_publisher` | 发布新快照、声明替代（若负责人批准该职责） | 批准自己提交的撤销 |
| `policy_auditor`（草案） | 只读撤销事件、替代关系、审批链 | 创建、批准或修改任何事实 |

若负责人不接受新增 `policy_auditor`，可让现有独立复核角色拥有 `pricing:retire:read`；但不得复用 `pricing:publish` 作为撤销批准权限。实现前需由负责人确认角色是否按公司/数据类别进一步分域。

## 5. 审计要求

每次申请、批准、拒绝、撤销事件作废和替代声明都必须形成追加审计记录，至少包含：

- 目标发布快照 ID、策略 ID、公司 ID、数据类别；
- 动作类型、结果、操作者自然人主体 ID、角色快照；
- UTC 时间戳、必填原因、可选外部工单引用；
- 事件 ID、前序事件 ID/版本、请求幂等键和内容指纹；
- 若是替代关系，记录新旧发布快照 ID。

撤销原因不得为空白或仅由占位符组成。审计记录不可更新、不可删除；更正通过新事件表达。审计和备份保留 `TEST` 与 `PRODUCTION`，这与 RF-PM-050 的业务页面过滤边界一致。

## 6. 与 RF-PM-032 距离计价的关系

RF-PM-032 的距离计价和改址/改时重核价必须使用报价当时选定的发布快照及其数据类别，不自动切换到“最新”或“未撤销”的策略。

- 已生成报价在策略撤销后仍按自身快照有效期处理；重核价是一次新的报价计算，必须重新选择一个当前可用且类别相容的策略，并在结果中记录新快照 ID。
- 若原策略已撤销且业务要求重核价，系统应返回“原策略已撤销，需要重新选择策略”的可操作错误，不静默替代。
- 距离计价的计算规则、费用分配和现有 RF-PM-032 审批边界不因撤销事件改变；撤销只改变策略可选性和审计链。
- `TEST` 报价不得重核价到 `PRODUCTION` 策略，反向亦然；类别一致性由 RF-PM-050 的设计统一定义。

## 7. 迁移与存量数据

不需要回填现有发布记录。历史发布快照默认视为“无撤销事件”；其有效期仍按原字段判断。实现时只需为新事件表建立空集合、索引和读模型兼容逻辑，不改写旧行、不生成伪造的撤销人或原因。

若未来需要把历史业务事实标注为 `TEST`／`PRODUCTION`，由 RF-PM-050 另行设计回填脚本；该脚本只能输出数量和失败计数，不读出或打印记录内容。RF-PM-049 不引入迁移脚本。

## 8. 备选方案与不选理由

### 方案 A（推荐）：追加撤销事件 + 独立复核

优点：发布记录不可变、撤销可审计、职责分离清晰、可表达撤销作废和并发控制。缺点：需要事件读模型和新增权限。

### 方案 B：在发布快照上增加可变 `status=RETIRED`

不选：会改写不可变发布事实，难以保留谁在何时以何因撤销，也容易绕过独立复核。

### 方案 C：发布新策略即自动撤销旧策略

不选：把“替代意图”和“错误停用”混为一谈，无法保留回退策略；也会让发布人间接改变另一条记录的默认可用性。

### 方案 D：增加 `dataClass: TEST/PRODUCTION` 解决撤销

不选：数据类别用于测试/正式隔离，不表达策略生命周期；它是 RF-PM-050 的设计领域，不能替代撤销和替代审计。

## 9. 与 RF-PM-050 的先后与重叠

两张设计卡共享 `dataClass`、根记录、关联继承、业务页面过滤与“审计/备份不过滤”的术语。先后顺序为：

1. RF-PM-049 先确定策略撤销/替代的状态、审批和事件术语；
2. RF-PM-050 在这些术语上定义测试/正式类别、关联继承和页面过滤；
3. 两份设计一起接受负责人侧 Claude 审查，但任何实现必须在各自设计批准后另立实现卡。

重叠部分只限于：策略的 `dataClass`、类别一致性校验、审计保留和备份保留边界。RF-PM-049 不设计测试数据回填或页面开关；RF-PM-050 不设计撤销事件、撤销权限或替代关系。

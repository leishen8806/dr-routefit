# Telegram 用户端与司机双平台 App v0.1

2026-10-25 · 产品形态已由用户确认，交互与技术细节为开发草案，尚未接通 Telegram 或交付安装包。

本增补替代此前“客户以普通手机网页为主、司机仅 Android”的入口规划，不重编正式 PRD、RULE、AT。V1.4 冻结时统一收录。渠道选择不改变订单、报价、履约和财务的业务权威。

## 1. 各端定位

| 端 | 产品形态 | 核心职责 |
|---|---|---|
| 发货人／商户用户端 | Telegram Mini App＋Bot | 下单、确认报价、付款入口、订单跟踪、账单／COD、异常申请 |
| Bot | 私聊中的引导下单与消息入口 | 逐步填写或粘贴外部订单信息、确认摘要、查询进度、通知及客服转接 |
| Mini App | Telegram 内的移动网页 | 复杂表单、地图选址、照片预览、费用拆分、订单与账单明细 |
| 司机端 | iOS＋Android App | 当前工作位置地图、接单、取货核对、导航、签收、异常、离线证据、收入与提现申请 |
| 运营／调度／财务／仓库 | 既有角色工作台 | 沿用订单和财务权责；不迁入 Telegram 私聊 |
| 收货人 | 授权的单订单轻量入口 | 保留无需 Telegram 的访问路径；只读链接不获得写权限 |

不另建独立原生客户 App。企业客户桌面查账入口保留为辅助入口，不要求在手机上完成全部财务工作。Bot 与 Mini App 使用同一客户身份映射、草稿和业务服务，不各算价格、各建余额或重复生成订单。司机 App 技术框架、最低系统版本和分发方式仍由 D24 确认，不在本次默认选定 Flutter、React Native 或原生技术。

## 2. 用户下单闭环

首次启动 → 选择高棉语／英语／中文 → 验证并绑定获授权客户身份 → 新建草稿 → 填写取送联系人、电话、地址及货物 → 区域与货物校验 → 确认报价和交付安排 → 提交申请 → 先付款或获批月结 → 调度受理派单 → 跟踪／签收证据 → 账单／异常处理。

- Bot 下单不是只有跳转按钮：支持逐步收集必填信息、返回修改、取消草稿、查看完整摘要及明确确认提交。地图和多图等复杂编辑可打开 Mini App 后返回同一草稿。
- 粘贴订单内容只产生待确认字段，不直接下单。缺失尺寸、电话或歧义地址必须提示补充，不用猜测值确认适配。提交成功返回同一业务订单号。
- 配送价格与保险价格分列；保险独立记账、不参与平台与司机分成；COD 单列，不混入配送付款。
- 价格、区域、货物、时间或交付要求改变时，重新计算并确认报价版本。客户确认不表示车辆已接受，也不表示时效承诺已经成立。
- Bot 确认按钮与 Mini App 提交共享草稿版本及业务幂等键；重复点击、消息重投、两端同时提交只能形成一张订单。旧消息按钮失效后引导打开最新订单，不恢复旧价格或旧状态。
- 取消、改址、退款、争议分别走对应申请及审核，不直接改已生效的履约或账务记录。
- 首个客户交付闭环纳入受控自助下单；原 C3 中完整开放注册、批量下单和企业内部多级审批仍不自动提前。使用现有受邀客户范围，不把 Telegram 登录视为通过业务准入。

## 3. 页面与菜单

Mini App 沿用“寄件／订单／消息／我的”；寄件拆为取送信息、货物与附加服务、报价确认三步。订单详情分别展示履约、客户付款、COD 返还及异常状态；“我的”提供地址、主体切换、语言和获授权账单。财务明细按角色显示，不公开采购价或内部利润。

Bot 菜单：下单、我的订单、账单、客服、打开 Mini App。通知只给必要摘要及受控入口，不在群聊披露电话、完整地址、银行账户或账单。发送成功不等于已读、同意或签收；发送失败留待办和人工联系入口。

司机 App 沿用“任务／订单／我的”。任务页地图优先，显示定位来源、时刻和离线／定位失效状态；订单含已超时、配送中、已完成、已取消标签，并区分待接提案。流程按钮在底部菜单上方，右滑打开核对确认，不能跳过凭证和状态检查。收入、可申请提现、审核中、已付待核对分别呈现，不做可自由划转的钱包。

三语、字体、Logo、语义色、Toast、图片上传预览和强通知沿用现有标准。Mini App 后续需适配 Telegram 安全区、返回及关闭行为；退出前保留草稿，不能退出即提交。当前网页演示仍用 DEMO 口令；真实 Telegram 登录不要求用户输入 Telegram 密码或验证码给 Bot。

## 4. 接入与接口差距

已有 customer、merchant、driver 业务接口继续复用。Bot 适配层调用同一受限客户业务服务，不能以内部管理员身份代下所有订单。

| 待补能力 | 开发约束 | 当前状态 |
|---|---|---|
| Mini App 登录交换及解绑 | 服务端验证原始 initData、有效时段和重放；映射内部主体及成员权限，不信任 initDataUnsafe、用户名或客户端自报 customerId | 尚未写入 OpenAPI／实现 |
| Bot 更新接收 | HTTPS webhook 校验 secret_token；按 bot_id＋update_id 防重复；持久化接收后异步处理；重投不重复下单 | 尚未写入 OpenAPI／实现 |
| 会话与草稿续填 | Telegram 身份＋私聊＋业务主体隔离；持久草稿、过期、撤销、版本与两端幂等；多人共享群不作为下单身份 | 尚未写入 OpenAPI／实现 |
| 客户建单与提交 | 复用 customerCreateOrder、customerSubmitOrder；由原 C3 提前至受控下单 C1-ORDER，完整自助范围仍留 C3 | 本轮同步阶段元数据，非已上线 |
| 司机设备与通知 | iOS／Android 会话、设备注销、推送令牌生命周期、工作定位及失效状态；不把推送到达当接单 | 待专门接口与真机验证 |

Telegram initData 验证及字段可信度以 [Mini Apps 官方文档](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)为依据；webhook 校验与重试以 [Bot API 官方说明](https://core.telegram.org/bots/api#setwebhook)为依据。身份有效仍需检查对象权限；换绑不凭公开用户名转移企业或财务权限。Bot token 仅服务端保存，不写入网页、App、GitHub 或日志。

KESS 商户尚未开通，继续模拟。Telegram 不意味着 KESS 已成为 Telegram 原生支付提供商；实际收银台跳转、回跳与渠道查询需商户资料及内嵌浏览器联调。关闭支付页、客户端回跳或 Bot 消息不证明支付成功，付款未知先查原交易。核销、银行结算和双人控制不变。

GitHub Pages 仅发布静态演示／前端资源；真实 Bot webhook、身份验证、订单服务及支付查询需要服务端。司机安装包需要独立构建、签名和分发，网页或 PWA 不算已交付 iOS／Android App。

## 5. 验证与下一步

先做 Telegram 下单、订单状态与费用页面的模拟闭环，再实现共用业务服务、Telegram 适配及司机双平台工程。保持 KESS 模拟，取得商户资料后才做真实渠道验收。不要让渠道拆分延迟基础计价和合理派单。

新增验收候选（不是正式 AT，均待执行）：

1. 同一客户从 Bot 填到一半，在 Mini App 继续；重复提交、消息重投只生成一单。
2. 伪造／过期 initData、非法 webhook、旧确认按钮及跨货主访问均被拒绝。
3. 两端展示同一报价，保费不参与分成；报价变化要重新确认；未付款且无获批月结不能派单。
4. Bot 关闭或消息未送达不改变订单；用户可在 Mini App 查真实状态；通知失败有负责人处理。
5. iOS／Android 真机验证前后台、锁屏、断网、进程终止与定位撤权：不承诺永续后台定位，过期位置显式标记；离线不能接新提案，证据补传逐项判定。
6. 两平台验证任务右滑确认、拍照上传、导航返回、重复签收防护和紧急异常；拒收／事故不直接完成订单。
7. 收货人无 Telegram 仍可通过授权轻入口跟踪；客户账单确认不能替代内部复核审批。

本轮仅同步范围、接口阶段和网页入口说明；未创建 Bot、发送消息、创建移动工程、取得设备权限、提交应用商店或部署服务。

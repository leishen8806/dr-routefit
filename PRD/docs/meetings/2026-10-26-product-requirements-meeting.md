2026-10-26 · 会议目的：冻结首期试点的业务闭环与决策责任，不把原型、接口数量或本地测试当作生产上线批准。

## 一页结论（开场 5 分钟）

- 产品基线：`PRD-V1.4-review.md` 已汇总当前范围，但状态仍是**待产品与技术冻结**；正式 PRD/RULE/AT 编号尚未改写。
- 首期应验证的闭环：**受控录单/导入 → 报价确认 → 预付或获批月结 → 合规派单 → 司机取送与签收 → 财务核验与应付/异常追踪**。
- 优先级已明确：安全与合法装载是硬约束；在可行方案中依次考虑准时送达、车辆适配、顺路拼单和成本。
- 本地接口契约现有 235/235 项实现映射，单元测试 86/86、KESS 适配器测试 7/7 通过；这只是开发证据，尚无 PostgreSQL 集成测试环境、KESS 沙箱商户或生产部署。
- 本次会议最重要的输出不是“继续加功能”，而是确定**单仓试点边界、付款与结算规则、首批渠道、负责人和验收门槛**。

## 会议目标与必须产出（60–75 分钟）

1. 确认 V1.4 是否作为当前产品冻结候选基线，以及冻结前必须补齐的决策。
2. 选定一个可验收的单仓/单城试点，而不是同时启动完整 WMS、公开平台、Telegram、iOS 和 Android 工程。
3. 确认首期客户、司机、调度、仓库和财务使用同一订单/财务事实的边界。
4. 明确本轮不做的内容，避免把路线智能化、自动资金划转和移动端发布混进基础闭环。
5. 为每个决定指定一位人类负责人、证据、截止条件与下一次复核时间。

## 已确认、无需重新辩论的原则

- 所有候选方案先满足安全、重量、体积、装载尺寸、货物限制、司机时段和已承诺时间窗。
- 及时送不是“选择最快车辆”，而是在合格车辆中优先满足承诺时效。
- 顺路插单不得让任何已承诺订单超时，也不得突破装载约束。
- 履约签收、客户收款、司机交款、COD 返还和合作方付款是不同状态，不能压缩为一个“完成”。
- 财务敏感动作至少经独立复核和审批；首期不做自动银行划款、自动退款或钱包。
- 账户、身份、银行及支付凭据不进入原型、公开仓库、会议记录或日志。

## 首期范围：明确做与不做

| 首期试点闭环 | 后续/待条件满足后再做 |
| --- | --- |
| 受控录单/导入、货物与地址校验、报价快照、付款或月结门槛 | 公众开放注册、全量自助货运平台 |
| 自营/白名单合作运力的人工调度与司机接受 | 未验证的自动最优路径、自动插单、3D 装箱自动放行 |
| 仓库交接、签收/拒收/退回证据、异常责任链 | 快递柜/驿站网络、无人投放 |
| 应收、COD、司机现金保管、合作应付与人工复核 | 自动划款、自动退款、完整总账/税务 ERP |
| Telegram/门户的受控查询与申请设计、司机任务接口 | 正式 Telegram Bot 上线、iOS/Android 商店发布 |

## GitHub 整理方案（会后执行，需明确批准）

1. 从 `origin/main` 建立干净整合分支；保留当前工作区，不执行覆盖或重置。
2. 将本地工作按“需求/原型/接口与服务端/生成文档”拆成可复核提交，先运行对应测试。
3. 创建 Draft PR，注明本地数据库集成测试仍受测试库阻塞；不以单元测试替代该结论。
4. 确定至少一名独立审查人、分支保护和合并条件后，再合入 `main`。
5. 静态 Pages 与后端服务分开发布；Pages 成功不能作为后端、支付或财务功能验收。

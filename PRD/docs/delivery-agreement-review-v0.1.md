# 订单交付约定与收货授权差距评审 v0.1

2026-10-24 · **PROPOSED / 待评审增量**。承接用户的 2U 对标与交付体验材料；本文件不是正式冻结规则，不追加已批准开发任务。本轮不改 OpenAPI、Demo、正式 PRD、RULE/AT 或 SQL。研究事实与限制见[公开核查记录](research/2026-10-24-2u-delivery-review.md)。

## 1. 当前依据与需要纠正的前提

当前依据是 [V1.4](PRD-V1.4-review.md) 3.5–3.6、6、9、21.3.1，以及后续明确增补和[开发接口包](../../contracts/README.md)。V1.4 已区分承诺、预测、外部交付报告和凭证核验，不能另建相冲突的“扫描即签收”状态。

最新本地设计已包含邀请制货主门户、单订单收货人入口和阶段开关。因此“客户仍只有只读跟踪、所有客户写操作均未规划”的判断只适用于旧基线，不代表当前设计。接口存在不意味着上线，也不意味着需要独立原生 App。

本次建议的原则：先满足安全、实际装载、既有时效承诺及已确认交付条件，再在合格方案中比较成本。交付方式是可行性检查条件，不是另一项可以用低价抵消的评分；外部道路或现场事件仍可能导致失败，应如实进入异常，不能宣称系统保证零失败。

## 2. 已有与缺口（以当前文件为证据）

| 主题 | 已有 | 仍缺，不能当作已实现 |
|---|---|---|
| 时效与服务 | OrderDraft.serviceLevel、exclusiveVehicle；Promise 的原/新时间窗 | 独立交付方式和具体交接层级，当前 notes 不能承担结构化约束 |
| 地点 | Location 的地址、联系人、坐标 | 建筑入口/楼栋/楼层/房门/室内指定点的明确口径与进入条件 |
| 收货授权 | RecipientAuthorization、内部核验和司机读取；禁止司机自批 | 授权人、授权对象、范围、方式、时刻和撤销版本的结构化关联，目前主要落在证据文件 |
| 客户变更 | ServiceRequest、CaseDecision、新报价/承诺关联 | DELIVERY_METHOD_CHANGE、代收变更、付款方确认与收货方授权的独立状态 |
| 合作方适配 | Partner/协议版本、承诺检查；V1.4 快递凭证核验 | 结构化交付能力、代收/POD/附加服务能力及拒绝原因 |
| 交付记录 | DeliveryRequest 的货件、剩余件、授权和证据 | 本人/授权代收显示、证据策略版本、核验结论与约定版本的完整绑定 |
| 通知 | Notification 的投递状态；收货人验证另建模 | 通知成功不产生授权，授权必须是独立事实，不能由 readAt 推断 |
| 经营报表 | 财务下钻、费用独立、状态分离 | 原承诺达成、方式符合、首次交付、未收到争议的明确口径 |

上述 DTO 名称均来自当前 `contracts/openapi.json`。新增名称和字段如下均是**提议**，不得直接发送到当前接口；机器契约拒绝未知字段。现有 389 项形状样例也不证明以上缺口已补齐。

## 3. 候选数据模型：四个维度分开

| 维度 | 内容 | 不可推导 |
|---|---|---|
| 时效等级 | S1/S2/S3/S4、承诺窗口与预测 | 及时送不自动包含上楼或安装 |
| 交付约定 | 交接位置、本人或获授权代收、允许接收人 | 经济拼单不自动允许改成自取 |
| 附加服务 | 搬运/上楼/等待等已购买服务及边界 | 备注需求不代表能力已确认或已付费 |
| 交付证据 | 授权、实物交接、件数、POD 与核验 | 照片、GPS、通知或点击按钮单独不能证明交付 |

建议新增逻辑对象 DeliveryAgreement，作为订单下的不可覆盖版本；不另建独立系统。候选字段：

| 字段组 | 候选字段 | 责任和校验 |
|---|---|---|
| 绑定 | id、orderId、version、supersedesId、quoteId、promiseId | 同订单同有效版本；原承诺独立保留 |
| 主体 | requesterSubjectId、payerSubjectId、recipientPartyRef | 从已授权关系取值，不让客户端自行切换货主 |
| 地点 | addressVersionId、handoverLevel、handoverPoint、floor、accessRequirements | 位置层级使用可选枚举＋必要说明；楼层、进入限制按场景要求 |
| 方式 | deliveryMethod、authorizedRecipientRef | 首批候选 PERSON_HANDOVER / AUTHORIZED_DELEGATE；自取点/柜/无人投放默认禁用 |
| 服务/费用 | includedServiceCodes、excludedServiceCodes、additionalFeePolicyVersionId | 额外收费授权指向独立报价，不复制另一份金额账 |
| 证据 | consentRecordIds、evidencePolicyVersionId | 按角色/权限保留必要证据，客户视图脱敏 |
| 兜底 | exceptionPolicyVersionId、contactEntry | 无回复、无法进入、地址错走异常；不能默认允许投放 |

同意记录候选 ConsentRecord：谁、代表谁、对什么动作、针对哪个约定/报价版本、明确同意或拒绝、时间、验证渠道、证据、撤销情况。付款授权与收货授权分别保存，不用一个 `confirmed=true` 代替。身份资料按最小必要原则留存，不要求拍完整证件。

## 4. 变更与生效条件

提议流程：收到申请 → 服务/路线/装载/时效/费用评估 → 收集受影响方确认 → 原子发布新约定、必要的新报价和承诺 → 使旧执行授权失效 → 相关端刷新任务。流程阶段是本草案概念，不是已新增订单主状态。

| 情况 | 需要的确认 |
|---|---|
| 同一地点从本人交接改授权代收，无新增费用 | 收货人或合法授权方明确授权；承运能力/证据策略复验 |
| 收货人要求上楼、改址、二次配送产生新费用 | 收货安排授权＋相应付款方同意新报价；预付/有效月结门槛仍成立 |
| 下单方选择更便宜但只送自取点的方案 | 不能直接采用；当前自取能力未开放则直接排除，不能靠同意绕过能力禁用 |
| 一方同意另一方未回复/拒绝 | 保持待确认；不得把未回复或通知已读当同意 |
| 申请未生效但原方案仍安全可执行 | 按原约定处理；若出现无法进入等事实则走异常，不自动换交付方式 |
| 变更审批中司机已交付、或报价/计划变化 | 重新读取事实并核查；不把迟到的批准反写到过去交付 |

所有需更新的内部聚合在一个事务内校验版本并发布，通知用 outbox。外部承运商无法同步确认时继续显示待确认，不能凭发出通知就认定其接受新约定。对价变化不默认扣司机收入；保险与 COD 不参与配送费分成。

## 5. 对现有接口的候选影响

| 现有操作/结构 | 评审通过后的最小改动方向 |
|---|---|
| OrderDraft / CustomerOrderDraft / ExternalOrderRequest | 支持交付要求草案；旧来源缺失显示未明确，禁止默填允许代收 |
| Quote / Promise / checkPromise | 绑定有效约定或要求版本；报价明确包含服务，承诺检查含交付能力 |
| dispatchCandidates / createAssignment / createBooking | 先过滤交付方式/POD不符合者；同时说明价格与服务边界 |
| ServiceRequest / RecipientServiceRequest / CaseDecision | 增补方式/代收申请类型，分别关联收费确认与收货授权；不直接修改履约状态 |
| RecipientAuthorization / recordRecipientAuthorization | 扩充授权范围/对象/有效版本，变更或撤销使旧授权失效 |
| driverDelivery / bookingVerifyDelivery | 保存实际交接对象类别、约定及凭证策略版本，判定证据是否足够 |
| OrderDetail / CustomerOrderDetail / PublicTracking / recipientDelivery | 按权限展示已约定安排、更新时间和异常；公开链接不曝光代收人私人资料 |
| finance documents / Quote | 复用现有补差、退款和审核；不新增直接改余额入口 |

字段、路由和状态机需一起评审；只改一个前端按钮不能闭环。当前不新增猜测的可调用路径，不修改生成的字段目录或契约样例。

## 6. 页面变化建议（不重做 Demo）

录单/报价增加交接层级、服务包含/不包含、受影响方确认摘要；调度候选显示“方式不符/证据能力不足”等排除理由。司机任务在下一步滑动操作前展示本单约定及授权，滑动手势不等于收货人授权；离线不可确认新的授权变更。

货主门户看订单费用、已约定服务、变更待谁确认和异常进度；收货人轻入口只处理本单安排、授权和未收到反馈，不取得货主的加价批准权。仓库在装车交接时读取已生效服务要求，异常处理显示保管人和下一负责人。财务沿用独立收付/COD/交款/结算，不从 delivered 推导结清。

本人签收与授权代收用不同文字。照片/定位是辅助证据；没有智能手机可走已批准、留证且独立核验的人工路径。不得为了完成率把未到场、凭证不齐或仅收到外部扫描的订单显示为已交付。

## 7. 候选验收（DELIVERY-REVIEW，不占用正式 AT）

| 标识 | 场景 | 期望 |
|---|---|---|
| DRV-01 | 便宜候选仅支持自取，本单要求入口交接 | 排除，不降低原交付条件 |
| DRV-02 | 代收通知已送达/已读、收货人无回复 | 授权未成立；不能交付给代收人 |
| DRV-03 | 授权代收成功 | 显示真实类别/依据，不能显示本人已收 |
| DRV-04 | 改址或上楼加费，仅收货人同意 | 保持待费用确认；不自动计费/改线 |
| DRV-05 | 仅付款方同意无人投放 | 不替收货人授权；未开启能力仍拒绝 |
| DRV-06 | 旧授权绑定的地址/约定版本已变 | 拒绝用旧授权完成新任务 |
| DRV-07 | 部分件交接、其余拒收 | 保留实收、剩余和保管，不整单完成 |
| DRV-08 | 承运商 reported，但POD不足/收到未收到争议 | 保留原报告，待核验/争议；不自动关闭 |
| DRV-09 | 交付已核验后提出争议 | 追加争议和更正链，不删除原事实 |
| DRV-10 | 通知发送失败/结果未知 | 如实显示，进入联系兜底；不伪造授权 |
| DRV-11 | 同一变更并发批准或旧离线事件补传 | 最多一版生效；过时事件不覆盖新约定 |
| DRV-12 | 已交付但COD未核验/返还 | 履约与财务分别展示，金额不自动归零 |

上述均 NOT_RUN。本轮只做文档对照，不宣称增加了服务端守卫。

## 8. 指标候选口径与最小验证

按企业、服务、交付方式、业务时区窗口分别统计；原承诺到期队列固定，不因后续改约、异常或退款删单。无适用承诺或无数据另列数量，分母为0显示“不适用”。

| 指标 | 分子/分母候选 | 反作弊与未知 |
|---|---|---|
| 原承诺按时完成率 | 原期限内已核验完整交付数 / 窗口内原承诺到期订单数 | 到期未核验不进分子；原始/变更后指标分列，取消按原因另列 |
| 方式符合率 | 证据确认符合生效约定的交付数 / 全部报告交付数 | 未核验比例同时披露；变更与原方式符合情况分列 |
| 授权证据覆盖率 | 有对应有效授权的交付报告数 / 按策略需授权的交付报告数 | 不用上传附件数量替代有效授权 |
| 首次交付成功率 | 首次实际交付尝试完成并核验的订单数 / 有首次尝试的订单数 | 尝试事件不可删除；尚未核验单列 |
| 未收到争议率 | 在声明观察窗口内有该争议的去重订单数 / 对应交付报告队列订单数 | 观察窗口、成熟/未成熟队列分别展示，不混成固定发生率 |
| 异常处理时长 | 从异常创建至核实关闭的耗时分布 | 未关闭展示等待时长，不以提前关单美化 |
| 每单实际履约成本 | 同币种已确认成本 / 明确的订单队列数量 | 待确认成本和缺失成本单列，不填0；条件性退回费不是必然成本 |

最小验证是合成数据流程演练，不做市场验证：使用 12 个以上候选场景，让调度、司机、付款方、收货人分别按权限走单；重点验证两个独立确认与旧授权失效。建议限一天设计演练，成功标准为全部阻断场景无越权放行、每笔变更能解释责任与费用。任一未授权交付/加价即失败，先修设计再决定是否修改 OpenAPI 与 Demo；该演练尚未执行。

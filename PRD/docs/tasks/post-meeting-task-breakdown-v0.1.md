# 需求会后任务拆解 v0.1

2026-10-27 · 依据 [2026-10-26 产品需求会材料](../meetings/2026-10-26-product-requirements-meeting.md)、[基础配送闭环实施任务](../core-delivery-implementation-plan-v0.1.md) P01–P02、[双人开发分工](../development-responsibilities-v0.1.md) 与 [`ops/codex/README.md`](../../../ops/codex/README.md) 的分支和版本规则。基线：`develop` `a12b15f`。

## 1 决策依据

2026-10-27 项目负责人确认：会议结论与 M01–M09 的**推荐的最小答案**一致（含**会前评审意见**），已回填会议记录。本拆解据此执行：

| 编号 | 本拆解采用的结论 | 对任务的影响 |
| --- | --- | --- |
| M01 | V1.4 为冻结基线，冻结只补决策表 | P01 页面按 V1.4 与现有契约实现，不改 RULE/AT 编号 |
| M02 | 单仓试点；具体取值按 V1.4 §1.4 填写 | 页面开发先用合成区域、货类和费率（实施计划 §5 允许）；试点验收前必须有签批的 §1.4 |
| M03 | 普通配送＋明确交付方式；PILOT-0 不启用 S1（及时送） | 报价与受理页不提供及时送选项 |
| M04 | 已核验预付或获批未过期月结才可派单 | 属 v0.4.0（P02），本轮只拆前置决定 |
| M05 | 保险独立记账、不参与分成；COD、运费、合作应付分别追踪 | 报价明细单列保费；COD 首期是否启用随 §1.4“收款方式”决定，默认关闭 |
| M06 | 改址/改时先申请后重评估，加价须客户确认 | 改单重核价卡覆盖“确认后只能走候选报价” |
| M07 | 客户订单首期由运营代录或现有网页申请表进入；司机端为仅限试点司机的网页端 | P01 页面为运营端，不建 Telegram Bot 或 App |
| M08 | 当前采用 PostgreSQL 16，GeoCore 服务区落地时引入 PostGIS | 由 RF-DEC-04 写 ADR；不阻塞 P01 |
| M09 | 采用 V1.4 §15.1，补时限与具名人员 | 实车试点前必须完成 |

RF-DEC-01 的产物：[V1.4 冻结说明](../decisions/2026-10-27-v1.4-freeze.md)；RF-DEC-04 的产物：[ADR D24 数据库选型](../decisions/ADR-D24-database.md)。两者合入 `develop` 即视为项目负责人批准。

## 4 推荐顺序

1. 并行开始：RF-PM-022、RF-PM-024（页面）；RF-DEC-01、RF-DEC-04（文档）；RF-DEC-02、RF-DEC-03（运营）。
2. RF-PM-022 合并后开始 RF-PM-023；之后 RF-PM-025。
3. RF-PM-022–025 合并进 `develop` 后执行 RF-QA-02。
4. RF-QA-02 通过且 RF-PM-018 合并后，Claude 发 v0.3.0 发布 PR（`develop → main`）。
5. RF-DEC-05 有结论后拆 v0.4.0。

S1 及时送、Telegram Bot、司机原生 App、自动派单与路线优化、真实地图与 WMS 接入、生产部署。均保留原需求，不删除。

# RF-PM-050 · 测试数据分类与隔离设计（v0.4.0）

状态：设计草案，待负责人侧 Claude 审查并由 `leishen8800` 批准。本文只定义数据模型、约束和交互，不写实现代码、迁移脚本、API 契约或页面文件。

## 1. 目标、范围与共享术语

为试运营和开发环境中的合成数据建立结构化分类，避免测试客户、区域、订单、案件或策略混入正式报价、业务统计和运营页面。所有根记录使用明确的 `dataClass`：`TEST` 或 `PRODUCTION`；不得再用 `[TEST]` 名称前缀、创建人或关联关系猜测类别。

与 RF-PM-049 共用以下术语：

- **根记录**：拥有业务生命周期、可被独立查询或审计的记录；本设计覆盖客户、服务区域、订单、案件、费率草稿和策略发布快照。
- **关联继承**：订单/案件等关联记录从创建时绑定的根记录取得类别快照；类别不能在子记录上被任意改写。
- **发布快照**：不可变的费率策略发布记录；RF-PM-049 的撤销事件只影响默认可选性，不改写其 `dataClass`。
- **审计和备份不过滤**：两类数据都保留在审计流和备份中，过滤只发生在业务页面、统计和正式运营报表。

RF-PM-049 先定义策略撤销/替代的状态、职责和审计边界；RF-PM-050 在同一术语上定义测试/正式类别。两份设计一起接受负责人侧 Claude 审查，批准后分别另立实现卡。

## 2. 数据类别放置与关联继承

### 2.1 根记录

以下根记录必须有非空的 `dataClass`，值只能为 `TEST` 或 `PRODUCTION`：

| 根记录 | 选择类别的时点 | 说明 |
| --- | --- | --- |
| 客户 | 创建/导入时 | 客户的正式与测试身份不能通过同名合并；精确名称去重仍需遵守现有导入规则。 |
| 服务区域 | 创建/发布时 | 区域类别必须与可使用它的客户和订单类别一致。 |
| 订单 | 创建草稿时 | 从客户和初始区域取得类别快照，并拒绝不一致组合。 |
| 案件 | 建立案件时 | 继承关联订单类别；不允许跨类别挂接订单。 |
| 费率草稿 | 创建草稿时 | 只能引用同类别客户/区域的报价上下文。 |
| 策略发布快照 | 发布时 | 从策略草稿继承类别；RF-PM-049 的撤销/替代关系不能跨类别。 |

建议实现保存 `dataClass` 和不可变的 `dataClassSource`（例如“客户创建”“订单从客户继承”）以便审计，但字段名称由后续实现卡确定。

### 2.2 关联记录规则

- 订单关联客户、提货/送货区域时，三者类别必须一致；缺失类别或类别不一致时拒绝创建。
- 案件从订单继承类别；案件不能被移动到另一订单或另一类别。
- 费率草稿和发布快照只能选择同类别的订单上下文、区域和客户；策略发布时再次校验。
- RF-PM-049 的 `supersedesPublicationId` 关系必须同公司、同类别；撤销事件不改变类别。
- 任何需要把 `TEST` 记录用于 `PRODUCTION` 报价的动作都必须失败并留下安全错误，不得通过管理员页面绕过。

## 3. 业务约束：测试与正式数据隔离

### 3.1 报价与策略

- `TEST` 策略只能生成 `TEST` 客户的报价；`PRODUCTION` 策略只能生成 `PRODUCTION` 客户的报价。
- 读列表可以按类别筛选，但默认正式报价流程只读取 `PRODUCTION` 策略；测试工具必须显式选择 `TEST`。
- RF-PM-049 撤销后的策略即使仍有历史报价，也不得因为类别过滤被重新选入新报价。

### 3.2 创建和变更

- 创建订单、案件、费率草稿和策略发布时执行类别一致性校验。
- 客户或区域类别一经产生业务引用不得就地修改；若业务需要转换，另建目标类别记录并保留原记录及审计。
- 导入和批量操作必须显式声明类别或使用经过批准的导入上下文；缺少声明时拒绝，不根据名字猜测。

## 4. 运营页面与报表交互（只做说明）

运营页默认隐藏 `TEST` 数据，默认查询条件等价于 `dataClass=PRODUCTION`。页面提供“显示测试数据”开关：

1. 开关默认关闭，刷新页面后仍关闭，避免把测试数据带入日常操作。
2. 打开后在列表、计数和详情中明确显示“测试数据”标识，并在请求中显式传递类别筛选。
3. 关闭开关时清除测试数据的选中状态、分页游标和批量操作选择，防止把测试记录提交给正式动作。
4. 正式运营报表、报价确认和财务汇总不受该开关影响，始终排除 `TEST`；测试报表需单独入口或显式类别。
5. 空结果、混合类别和类别不一致错误要用可操作提示表达，不能只显示“无数据”。

本节只描述交互和线框语义，不修改任何页面文件。

## 5. 存量数据回填方案

存量数据按已有合成数据约定、导入来源和审计上下文回填 `dataClass`；无法可靠判断的记录进入待负责人处理队列，不默认标为 `PRODUCTION`。

回填脚本要求：

- 只输出数量：按根记录类型、`TEST`、`PRODUCTION`、未知/待处理分别输出计数；不输出客户名、地址、价格、策略内容或 ID。
- 先在只读/演练模式报告计数，再在明确批准后写入；每批次有幂等标识和事务边界。
- 不删除任何历史测试数据，不改已有审计记录；回填动作本身写入新增审计事件。
- 关联记录类别从根记录继承并记录冲突计数；冲突不能静默覆盖。
- 备份和审计包含全部类别，不能因为回填而过滤或脱敏成无法恢复的状态。

需要负责人拍板：未知类别是阻断发布，还是保留为 `UNKNOWN` 并禁止所有业务使用。设计不预设自动降级为正式数据。

## 6. 审计、备份与查询边界

- 审计记录保留数据类别、来源和类别校验结果；审计查询不按类别删除历史。
- 备份完整保留 `TEST` 与 `PRODUCTION`，恢复后类别和关联约束必须不变。
- 业务查询、统计、正式报表默认只返回 `PRODUCTION`；需要测试数据的工具必须显式声明并记录调用上下文。
- 权限过滤仍按现有主体/公司范围执行；数据类别不是绕过主体授权的替代品。
- RF-PM-049 的撤销与替代审计继续使用同一保留边界；撤销不能让测试数据从审计或备份消失。

## 7. 备选方案及不选理由

### 方案 A（推荐）：结构化 `dataClass` + 关联继承

优点：可查询、可约束、可审计，能够在数据库和应用两层阻断跨类别报价。缺点：需要存量回填、跨根记录校验和页面筛选。

### 方案 B：仅在名称前加 `[TEST]`

不选：容易漏写、可被重命名绕过，无法约束订单/区域/策略关联，也无法可靠过滤报表。

### 方案 C：仅按创建人或环境变量推断

不选：同一环境可能同时存在两类数据，历史迁移和导入无法稳定复现；无法提供业务层审计事实。

### 方案 D：只在页面层隐藏测试数据

不选：接口、报表、报价计算仍可能读到测试策略；安全边界必须在业务约束和查询层同时成立。

## 8. 与 RF-PM-049 的职责分工和先后

1. RF-PM-049 确定策略撤销/替代的事件、审批、角色和不可变发布语义。
2. RF-PM-050 复用这些语义，为策略发布快照和其他根记录增加 `TEST`/`PRODUCTION` 类别与继承规则。
3. 两份设计一起评审；任何实现必须等各自设计批准后另立实现卡，且不把一个设计的实现偷偷带入另一个 PR。

重叠仅限于策略发布快照的类别、跨类别引用拒绝、审计和备份保留。RF-PM-050 不设计撤销事件或新权限；RF-PM-049 不设计测试数据回填、页面开关或报表过滤。

## 9. 待负责人拍板的问题

1. 根记录的 `dataClass` 是否允许 `UNKNOWN` 过渡态，还是未知数据必须完全阻断业务使用？
2. 订单类别是否在创建时永久快照，还是允许在未提交草稿阶段重新选择客户类别？
3. 页面“显示测试数据”开关是否需要单独权限，还是沿用现有运营读取权限？
4. 回填是否按根记录逐类分批，还是在同一事务中同时处理客户、区域、订单和策略？
5. 正式报表是否允许负责人显式导出包含测试数据的诊断副本；若允许，如何命名与审计？

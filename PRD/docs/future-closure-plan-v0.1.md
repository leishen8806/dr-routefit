# DR RouteFit 后续闭环功能执行规划

v0.1 草案，2026-10-24。依据[闭环需求增补](closed-loop-requirements-v0.1.md)、V1.4 评审稿及用户后续确认。本文细化功能交付顺序、页面、领域动作、异常出口和验证条件；不修改正式 PRD 正文、RULE/AT 编号或 Gate 状态。下文 F01–F09 仅为规划工作包标识，不是验收编号。新增枚举、资源与路径均为候选契约，尚未实现或冻结。

## 1 当前起点与推进顺序

**最新优先级覆盖：**用户随后明确“先把平台跑通、基础价格计算不出问题、派单合理、降本”，以[平台执行基线](platform-first-execution-baseline.md)为准。先做统一报价、预付/月结派单守卫与正常配送核账；下文 F01–F09 作为保留的后续功能池，原“先部分退款”顺序暂缓，不再据此扩展当前切片。

F03/F05 最新增补见[合作单位／个人结算与资金管理](partner-settlement-and-funds-v0.1.md)：周期对账、个人申请／企业账单、统一应付占用、付款核验及资金日历。个人周结／企业月结为建议，需协议确认；不把结算沉淀当平台利润，不因客户月结未收自动延付承运方。

本轮已交付 F03/F05/F08 的按主体账期与财务提醒 Demo 子集：账单草稿/确认、模拟发送、催收暂缓/部分核销、付款入口及消息联动。证据见[本轮记录](../../prototype/records/2026-10-24-settlement/README.md)。其他资金日历预测、后台调度、真实通知和银行接口仍保留为计划，不能把本切片视为全部功能包完成。

已记录的原型证据是 112 项本地测试及正常/全部退回浏览器链路，见[最近闭环记录](../../prototype/records/2026-10-24-closure-update/README.md)。本次仅更新文档，不把历史测试计作新功能证据。Demo 的 B 全免政策只适用于合成的未收款、未投保场景，不是正式退款制度。

建议顺序：F01 部分交付与售后事实 → F02 费用与退款 → F03 收入提现联动；F04 事故、F05 多运力复用前述事实和账务；F06 用户/仓库接入统一订单来源；F07 完整仓储作业按实际权威边界接入。F08 只读投影随各包同步更新，不能推迟 R1-V 的真实接入验证。F09 仍按 R2 → R3-A/B/C 推进，不因 Demo 中出现路线图而前移正式算法阶段。

不预设人日或上线日期。每包先固定业务策略、输入和通过条件，再估工；功能已有原型不代表服务端与真机成本为零。

## 2 功能包及闭环定义

### F01 部分签收与退回检验

- 入口：司机任务 D05/D07、调度异常 W14、退回 W15、仓库点收 W13；客户授权查询只显示本单结果。
- 流程：逐件或货物行记录实收 → 对未收货物登记拒收/破损原因 → 调度指定退回目的地并复核 → 司机执行 → 仓库点收差异 → 检验 → 可用、维修、隔离或报损处置 → 实物异常结案。
- 数据：订单行/件号、数量、当前保管、交接双方、凭证、原因、退回任务和检验记录。收件人取得的件与司机剩余件分开；途中退货继续占用车辆容量。
- 阻断：未授权不能退回；到仓不等于点收；少件不能填成全收；点收不等于检验合格；客户要求全单取消不能抹除已交付件。
- 完成条件：每件货都有确定去向；无法找到的件保留显式差异案件和负责人，不能当作已返仓。财务争议可继续开放，不能借实物结案自动关闭账务。
- 合成例：10 件客户收 6 件、司机持 4 件；仓库仅点到 3 件时，1 件仍为司机保管差异，不能恢复 4 件可售库存。真实失货经批准另记处置与责任，不伪造交接。

### F02 费用裁定与已付款退款

- 入口：用户售后申请、客服/运营案件、财务订单账页；退回/取消/履约异常可以关联同一案件，禁止重复生成互相独立的赔付。
- 流程：事实核实 → 配送费、附加费、保费分别裁定 → 客户确认所需变更 → 审核 → 对未收款调整应收，对已收款建立退款任务 → 人工执行凭证或渠道结果 → 核对退款 → 分成冲正/应付调整 → 关闭财务案件。
- 区分三件事：应收调整改变应该收多少；退款改变已收款的去向；司机收入调整改变平台与司机之间的应付。不能将任意两项直接抵消。
- 失败出口：拒绝申请有原因及复核入口；支付结果未知保持挂起并查询同一业务请求；明确失败后才按同一退款任务创建受控新尝试；退款成功不能回改原收款为“未收”。
- 金额核对：同币种成功退款与未终结退款预留之和不得超过该来源已核验可退余额；资金来源、受益方与退款对象需匹配。运费、COD、保费和合作方应付不能跨账抵扣。
- 合成例：已核验配送 $20、保费 $2；裁定只退配送 $8，保费是否可退另有保单依据，成功后客户净支付 $14。**不能据此把司机收入自动改为净配送费的80%**；按用户后续确认，已完成服务保留应付，司机收入另经责任核实与人工批准调整。保费不参与分成，原分成和调整分别留账。

### F03 收入冻结与提现

- 入口：司机“我的/收入/提现”、财务提现队列、账户及银行卡管理。
- 流程：订单收入满足确认条件 → 可用余额 → 提现申请原子预留 → 财务审核 → 人工付款登记 → 独立到账核验 → 扣减预留并记已付。
- 驳回或获准撤销释放预留；付款处理中、结果未知或已成功时不得重复释放/再次付款。修改银行卡只影响后续申请，当前任务保留脱敏账户版本；付款前账户风险变化转复核。
- 退款与提现并发：同一余额不能既提现又冻结。收入已经付出后出现退款，记明确的待处理追偿/调账，不擅自使可提余额为负或自动扣司机其他订单款。
- 合成例：可用 $30，申请 $20 后可用 $10、预留 $20；未知付款结果仍预留 $20，不能再次申请同一笔资金。
- 待确认：收入确认时点、争议冻结范围、申诉与追偿政策、手续费承担。用户已确认“可申请、财务人工审核”，无需重新选择是否允许提现。

### F04 事故分散转运

- 调度先停用事故车辆；记录安全允许交接的依据后，按件给合规接驳车创建子任务；接单、实际交接、签收各自确认。
- 父订单保留原承诺、客户收费与责任案件；子任务记录实际承运、区段、货物和救援成本。接驳报价不是对客户自动加价的授权。
- 件号不可重复分配；接驳车拒绝时仅释放其计划预留；货物已交接后必须通过新交接退回，不能撤销按钮直接还给原车。子任务部分失败不影响已完成件的事实。
- 完成条件：父子件数守恒，原车持货清零或差异显式处置，每个子任务有签收/退回结果；客户账单仅核算一次，救援应付独立核对。

### F05 合作车辆与人工快递应付

- 准入有效期/货类/服务窗口 → 合作司机提案或快递委托 → 实物交接 → 外部签收申报 → 内部核验 → 应付确认/争议 → 人工付款及核对。
- 快递取消未确认不得改派另一执行；外部超时不得当作取消成功；回传重复去重、乱序保留事件时间、矛盾状态转人工裁定。
- 退回后的配送费退款与承运商应付分开裁定，不假定客户退款就能自动扣承运商款。权限撤销不丢弃其正在保管的货物任务。
- 完成条件：没有互斥有效执行重叠、实物去向闭合、应付与付款及争议明确。沿用 R1-M，不新增开放司机市场。

### F06 用户和外部仓库订单接入

- 来源订单/粘贴文本 → 草稿核对联系人、取送地址、坐标、包装尺寸、服务等级和独享标志 → 配送区域/超距计价 → 配送费与保费报价版本 → 客户确认 → 请求调度 → 执行结果回传 → 回传失败重试/人工核查。
- 同企业、来源系统、外部订单号去重；相同外部标识不同关键内容进入修订，不能静默覆盖已承诺单。导入重复不能重复预留库存或收费。
- 在请求确认时重新检查报价、区域与承诺版本；禁送区不能用加价绕过。客户修改地址/时间须生成变更申请，不直接修改司机手中的任务。
- 客户 APP 和仓库系统分别认证，不能借中控只读凭据发派单请求。用户申请不等于自动派发，派发仍经安全与时窗约束。
- 完成条件：来源单到内部订单一一可追溯、客户确认可证明、回传可重放、不重复执行业务。

### F07 仓储入出库与退货处置

- 入库通知 → 实收差异 → 待检 → 合格入可用 → 订单预留 → 拣货复核 → 出库交接；退货先待检，再按处置决定归可用、维修或报损。
- 每仓明确自建库存或外部 WMS 为权威；RouteFit 的派单和点收不能在两个系统中各扣一次库存。跨系统失败进入待同步队列，使用对账修复而非静默双写。
- 盘点先冻结对应范围或采用批准的差异策略，调整保留依据。批次、有效期、序列号和库位按货品要求启用，不默认所有商品都需要。
- 完成条件：期初 + 已确认入库/调入 − 已确认出库/调出 ± 批准调整 = 期末；可用/预留/待检分别可追溯，预留不重复从实物总数扣减。

### F08 全端通知与只读中控

- 每个领域动作提交后产生事件，通知和快照消费事件；发送失败不回滚已完成实物交接，也不把未通知视为客户已同意。
- 手机强通知需提供处理入口与暂停/确认收到，确认收到不等于异常结案；声音服从用户设置，三语文案不改变业务枚举。
- 快照按授权受众显示正常交付、部分交付、退回、资金差异、库存待检与数据时效；失联标未知，不填合成值假装在线。
- 完成条件：同一业务版本在用户/司机/运营/财务/中控投影一致，隐私字段按角色减少；所有跳转重新授权，中控没有写业务状态的接口。

### F09 推荐与动态拼单

- 影子建议与人工派单比较 → 人工确认推荐 → 同仓合单 → 途中插入取送点 → 独立返程任务。每步重新验证所有承诺、逐段容量、车型货类、装卸顺序、工作时间和方案版本。
- 提案过期或司机拒绝保持原路线；并发确认必须原子检查车辆/货物/路线版本及预留。未知装箱结果转人工复核或排除，不能当作可行。
- 完成条件：明确可行、不可行和未知原因；无解不能自动放宽约束。路线时间与复杂装箱需真实技术样例证明，Demo 格位不替代实际装载证据。

## 3 下一切片与最小功能验证

下一切片限定 F01/F02：一笔订单、异质货物行、部分交付、剩余返仓、部分退款、保险不分成、司机收入调整；不同时引入自动银行划款或一般 3D 求解。

先准备可重复的合成用例：正常部分交付；返仓少件；重复离线签收；报价/任务版本过期；退款超额；退款结果未知；退款成功回调重复；退款与提现并发冻结；已付司机收入需人工追偿。每例包含操作主体、前态、货物去向、金额账项、后态和证据。

成功门槛是所有用例达到预期且没有重复交接、超额退款、余额重复占用或越权；出现任一错误即停止扩展并修复该包。先完成模型与契约、再做浏览器联动；真实接口和设备阶段另测，不承诺目前无依据的完成时间。

## 产品需求文档 PRD V1.0

**项目代号：** DR-DISPATCH  
**文档状态：** 待产品及技术评审  
**业务范围：** 柬埔寨本地货运、仓配配送、企业物流、顺路拼单  
**优先服务区域：** 金边及周边地区

# 1. 产品概述

## 1.1 产品定位

建设一个结合货拉拉式即时货运调度与顺路拼单配送的智能物流平台，实现订单、车辆、司机、货物、路线、时效、费用及运输状态的统一管理。

系统既支持仓库发出的配送任务，也支持外部企业和个人发起的同城货运需求。

主要提供两类能力：

**A. 智能运力调度**

系统根据订单时效、取送位置、车型、剩余载重、货物体积、司机位置和车辆可用时间，推荐合适的车辆与配送方案。

**B. 顺路拼单配送**

车辆已经具有既定运输任务时，允许符合条件的新订单加入路线，在不影响已有订单承诺的前提下，提高车辆利用率、降低空驶里程和配送成本。

## 1.2 业务目标

- 提高及时送订单的准时完成率。
- 降低车辆空驶和无效绕行。
- 提高车辆空间和有效载重利用率。
- 减少调度员的人工计算工作。
- 提供可追溯的司机接单、装车、运输及签收流程。
- 为 W1/W2/W3 仓配运营大屏提供可靠的调度数据。
- 形成可以逐步扩展至第三方司机与承运商的平台能力。

## 1.3 V1 范围

V1 优先支持受控车队与合作承运商。

包括：

1. 订单创建和服务等级。
2. 车辆、司机及运力管理。
3. 货物尺寸、重量和装载约束。
4. 人工调度和智能推荐派单。
5. 及时送时效保障。
6. 现有路线顺路插单。
7. 司机接单、取货、运输和签收。
8. 异常监控及调度员干预。
9. 调度报表与审计日志。
10. DR 仓配系统的只读状态对接。

V1 不直接建设开放式社会司机交易市场，不实现未经人工授权的资金自动划转，不控制真实物流设备，也不承诺没有验证过的实时定位或运营数据。

# 3. 核心业务规则

## 3.1 调度优先级

优先级分为两层：硬约束和优化目标。

### 硬约束（不得突破）

- 遵守车辆核定载重和安全要求。
- 货物必须能够实际装入车辆。
- 不得违反客户对特殊货物的运输要求。
- 不得违反已确认的订单时间窗。
- 司机和车辆必须具备执行该任务的资格及可用时间。
- 不允许订单被重复接单、重复装车或重复签收。

### 业务优化顺序

**第一：及时送承诺**

优先保证及时送订单能够在承诺时间内完成。

**第二：配送任务可完成性**

保证车辆、司机、装卸条件和取送路径均满足要求。

**第三：顺路拼单**

在满足所有已有订单承诺的条件下，优先利用已有路线的剩余运力。

**第四：配送成本优化**

在满足上述要求后，综合考虑距离、时间、车辆成本、司机补偿和空驶率。

此规则采用分层约束及排序，不采用一个可以让低成本抵消超时风险的简单总评分。

## 3.2 服务等级

| 等级 | 名称 | 调度策略 |
|---|---|---|
| S1 | 及时送 | 最高业务优先级，按已承诺的取件／送达时间窗调度 |
| S2 | 当日送 | 当日指定时间窗内完成 |
| S3 | 预约送 | 在客户选择的预约时间窗执行 |
| S4 | 经济拼单 | 优先利用顺路运力，按已明确接受的较宽时间窗执行 |

**规则：**及时送不能因系统希望提高拼单率而被延误。经济拼单也不能擅自超过已经承诺的时间。

若系统无法形成满足时效的方案，返回明确的不可承诺状态，交由调度员增加运力或与客户重新确认，而非自动承诺不可能实现的时限。

# 4. 订单管理模块

## 4.1 订单数据

每笔订单应包含以下信息。

**基础数据**

- 订单 ID、企业 ID、客户 ID。
- 服务等级。
- 创建时间及订单来源。
- 订单联系人。
- 发货地址及经纬度。
- 收货地址及经纬度。
- 取货时间窗。
- 最晚送达时间。
- 订单备注与特殊要求。

**货物数据**

- 货物类别。
- 件数。
- 每件长、宽、高。
- 每件重量。
- 包装类型。
- 是否允许堆叠。
- 是否允许旋转。
- 是否易碎。
- 是否不可倒置。
- 是否需要温控。
- 是否需要特殊装卸设备。
- 是否需要上楼、安装或其他增值服务。

**费用数据**

- 基础运费。
- 距离费。
- 及时送附加费（如适用）。
- 搬运和上楼费用。
- 等待费用。
- 顺路拼单优惠。
- 调度员授权调整。
- 最终客户确认金额。

价格项目与金额均由配置及报价规则产生，不使用硬编码的示例金额冒充正式报价。

## 4.2 订单状态

订单状态与车辆运输任务状态必须分开。

建议订单生命周期：

`draft → pending_validation → awaiting_quote → awaiting_dispatch → assigned → pickup_pending → picked_up → in_transit → delivered`

另设：

`cancelled / failed / exception`

状态转换必须定义执行角色、前置条件、审计记录和幂等规则。

特别要求：

- `assigned` 不等于司机已经接单。
- `picked_up` 必须有有效交接凭证。
- `delivered` 必须有符合规则的签收证明。
- 客户取消、司机拒单、系统重试不能造成重复派单。

- 资质与授权状态。
- 可驾驶车型。
- 工作时段。
- 当前任务。
- 当前状态。
- 接单与拒单记录。
- 有效位置及更新时间。
- 联系方式。
- 异常与服务记录。

司机位置不可用或已经过期时，应标记为位置未知，不能伪造当前坐标。

# 6. 货物体积与装载适配

## 6.1 基础体积核算

单件包装货物体积：

V = 长 × 宽 × 高

货物总体积为各件包装货物体积之和。

系统统一使用：

- 长度：厘米，内部转换为米。
- 重量：千克。
- 体积：立方米。

## 6.2 第一层：快速筛选

自动排除：

- 重量超过剩余有效载重的车辆。
- 总体积超过剩余容积的车辆。
- 货物单件尺寸超过可用装载空间且无法合法调整摆放的车辆。
- 车门尺寸不足的车辆。
- 货物运输要求不符合的车辆。
- 不满足取货及送达时间窗的车辆。

## 6.3 第二层：三维装箱

对于大件家具、门窗、板材、建材、托盘等，调用 3D Bin Packing 校验模块。

需要检查：

- 每件货物的实际三维尺寸。
- 是否允许调整方向。
- 货物间是否发生空间重叠。
- 是否满足堆叠限制。
- 是否能够经过装货门进入车厢。
- 是否存在必要的固定及装卸空间。
- 是否满足重量和装载安全约束。
- 是否影响其他货物的装卸顺序。

V1 对复杂异形货物、不确定包装或算法无法证明可装载的方案，允许标记为 `MANUAL_LOAD_REVIEW`，由具备权限的仓库或调度人员复核。

**装箱算法仅证明模型约束下的可行性，不替代实际装载安全检查。**

## 6.4 途中容量计算

顺路拼单必须对路线的每一段重新核算容量。

例如：

原路线：

仓库 → A → B

新增订单：

P 取件 → D 送件

系统必须确认在 P 取件之后至 D 交付之前，每一段的重量、体积及装载位置仍然可行。

不能只检查出发时的剩余体积。

# 7. 智能调度引擎

## 7.1 调度输入

- 待派订单。
- 已承诺订单。
- 司机与车辆信息。
- 车辆当前及计划位置。
- 可用时间窗。
- 货物尺寸和重量。
- 现有路线。
- 道路行驶时间矩阵。
- 服务等级。
- 装卸和停靠预计时间。
- 企业调度规则。

## 7.2 调度过程

**阶段 A：候选筛选**

过滤不符合硬约束的车辆和司机。

**阶段 B：时间可行性**

计算到达取货点、装货完成、预计送达及全部受影响订单的时间窗。

**阶段 C：装载可行性**

运行重量、体积、尺寸校验；必要时进行三维装箱。

**阶段 D：路线优化**

计算路径、距离、时间和顺路候选方案。

**阶段 E：推荐排序**

先排除不可行方案，再在可行方案中按服务等级、风险和成本排序。

**阶段 F：执行确认**

V1 的最终派单由调度员确认或司机通过授权流程接单。自动派单仅在已批准的企业策略范围内开放。

## 7.3 推荐结果结构

每个推荐方案至少返回：

- 方案 ID。
- 订单 ID。
- 车辆 ID。
- 司机 ID。
- 推荐路线。
- 预计取货时间。
- 预计送达时间。
- 剩余时效缓冲。
- 装载可行性结果。
- 各路段剩余容量。
- 是否属于顺路拼单。
- 新增距离。
- 新增时间。
- 预计配送成本。
- 风险原因。
- 不可行时的具体拒绝原因。

所有推荐结果必须附带计算时使用的数据版本和时间。

# 8. 顺路拼单模块

## 8.1 功能目标

允许一辆已执行或已规划运输任务的车辆，顺路承接新的快递、零担或其他适配货物。

适用场景：

- 仓库向同一区域配送。
- 金边市区跨区域配送。
- 商户之间的小件货物运输。
- 车辆返程顺路取件。
- 工程材料送货后利用返程空载空间。

## 8.2 拼单前置条件

必须同时满足：

1. 车辆和司机仍可接受订单。
2. 新货物可以安全装载。
3. 新取货点与送货点能够合理插入路线。
4. 原订单承诺不被破坏。
5. 新订单送达时间可满足承诺。
6. 插单费用与司机补偿满足业务规则。
7. 司机或调度员完成规定的确认。
8. 订单数据归属及调度权限合法。

## 8.3 插单算法

假设原路线已有 N 个站点。

系统尝试在可行位置插入：

- Pickup：取件点。
- Delivery：送件点。

必须满足 Pickup 在 Delivery 之前。

每个候选位置组合都要重新计算：

- 总行驶时间。
- 新增绕行。
- 原订单 ETA。
- 新订单 ETA。
- 司机可用时段。
- 每段车辆容量。
- 装卸操作时间。
- 成本变化。

输出多个可行方案，按照业务目标排序。

## 8.4 建议初始绕行规则

建议作为可配置的试点参数：

- 额外绕行时间不超过 15 分钟。
- 或不超过原剩余行程时间的 15%。
- 采用两者中较严格的限制。
- 及时送订单必须满足其时间窗及预先确定的可靠性缓冲。

这些参数属于试验假设，需要通过金边实际路网和配送记录校准，不是正式行业标准。

## 8.5 拼单异常处理

包括：

- 司机拒绝。
- 客户取消。
- 取货等待超时。
- 车辆故障。
- 道路封闭。
- 新订单尺寸与实际不符。
- 原订单预计超时。
- 途中额外装载失败。

发生异常时重新评估受影响的订单；必要时撤销未确认插单、改派或交由调度员处理。

不得在未重新确认的情况下擅自改变客户承诺时间。

# 9. 及时送保障系统

## 9.1 SLA 管理

每笔及时送订单必须有明确的承诺时间窗。

系统记录：

- 客户要求时间。
- 平台确认的承诺时间。
- 预计取件时间。
- 预计交付时间。
- 实际取件时间。
- 实际交付时间。
- SLA 状态。

## 9.2 风险预警

需要识别：

- 司机迟迟未接单。
- 车辆迟迟未到取货点。
- 实际装货超时。
- ETA 接近最晚送达时间。
- 路线异常。
- 长时间定位无更新。
- 新插单影响原订单准时率。
- 司机任务超出可用工作时段。

预警阈值由企业配置，不使用固定规则替代所有业务场景。

## 9.3 调度响应

针对风险订单，系统可推荐：

- 更换车辆。
- 寻找附近备用运力。
- 取消尚未确认的顺路插单。
- 调整尚未承诺的后续订单排序。
- 通知调度员。
- 由授权人员与客户协商新的时间窗。

所有人工覆盖、重新承诺和调度修改均应记录原因、操作人和时间。

# 10. 调度控制台

## 10.1 页面布局

建议由以下区域组成：

**顶部指标**

- 待派订单。
- 及时送待处理。
- 配送中。
- 已完成。
- 预计超时。
- 空闲车辆。
- 顺路拼单成功数。

**左侧订单池**

支持筛选：

- 服务等级。
- 企业客户。
- 仓库。
- 取货区域。
- 目的区域。
- 时间窗。
- 派单状态。
- 货物类别。

**中央地图**

展示：

- 车辆位置。
- 取送货点。
- 仓库位置。
- 已规划路线。
- 顺路推荐。
- 预计到达时间。
- 异常任务。

**右侧调度建议**

展示推荐车辆、司机、时效、剩余容量、装箱结果、绕行、费用及不可行原因。

**底部任务流水**

展示派单、接单、取货、出库、在途、签收、异常和改派事件。

## 10.2 关键操作

- 人工选择车辆。
- 请求智能推荐。
- 查看车辆装载空间。
- 查看推荐路线。
- 添加顺路订单。
- 检查插单对已有订单的影响。
- 确认派单。
- 撤回未执行的派单。
- 发起改派。
- 处理超时或异常。

所有写操作由授权业务服务完成，不能由地图或三维视觉对象直接改写订单状态。

# 11. 司机端

V1 可以先采用移动端 Web/PWA，技术评审后再决定是否开发原生 App。

## 11.1 核心功能

- 登录与身份认证。
- 当前任务列表。
- 接单或拒单。
- 查看取送货路线。
- 查看货物尺寸、重量和件数。
- 导航。
- 到达取货点确认。
- 扫码和货物交接。
- 开始运输。
- 到达送货点。
- 签收凭证。
- 上报异常。
- 查看任务历史。

## 11.2 签收要求

可按业务要求采用：

- 收件人确认。
- 电子签名。
- 照片凭证。
- 包裹扫码。
- 交付时间及位置记录。

照片和位置数据必须遵守最小必要、授权访问和留存期限要求。

## 11.3 顺路订单确认

司机应清楚看到：

- 新订单取送货位置。
- 货物类别、尺寸和重量。
- 预计新增距离与时间。
- 预计额外报酬。
- 是否影响原任务。
- 是否需要额外装卸。

V1 不在司机未确认且未获得明确自动派单授权的情况下强制追加任务。

# 14. 技术架构与开源复用

## 14.1 推荐组件

**业务调度参考：**Fleetbase / Fleet-Ops、OwnFleet。

**车辆路径求解：**VROOM。

**复杂取送货与约束优化：**Google OR-Tools。

**路网时间矩阵：**OSRM，可与当地地图服务方案对照。

**大件装箱：**独立评估 3D Bin Packing 开源库，完成算法正确性、许可和性能验证后再确定具体项目。

这些是技术候选，不代表已经批准直接集成。

## 14.2 分层架构

1. **业务 API 与数据层**：订单、车辆、司机、运单、认证授权。
2. **规则引擎**：服务等级、时间窗、货物适配、企业调度规则。
3. **装载求解器**：重量、容积、三维摆放可行性。
4. **路径优化器**：配送路线与顺路插单计算。
5. **调度执行层**：派单、司机确认、状态转换、签收与审计。
6. **地图服务**：路网、距离、ETA 和位置。
7. **运营控制台**：人工调度、推荐方案和异常处理。
8. **数字孪生只读层**：DR 三维场景与全景大屏。

调度服务不能依赖 Three.js 页面保持在线才能运行。

## 14.3 并发与幂等

必须满足：

- 同一任务不能同时分配给多个互斥承运方案。
- 推荐方案绑定路线版本。
- 确认插单前重新校验路线版本、司机状态及车辆剩余容量。
- 版本已变化则拒绝旧方案，要求重新计算。
- 接单、改派、取消、交接和签收使用幂等请求标识。
- 失败重试前确认原操作是否已经生效。
- 所有关键状态转换记录审计事件。

# 15. 非功能性要求

## 15.1 安全

- 企业和承运商数据隔离。
- 基于角色与对象归属的权限控制。
- 对敏感信息最小化授权。
- 调度变更可追溯。
- 不在日志中泄露敏感凭据。
- 第三方路线及定位服务按授权使用。

## 15.2 稳定性

- 外部地图服务故障时有明确降级状态。
- 优化器超时不会导致已经确认的订单丢失。
- 不可行方案必须返回结构化原因。
- 未确认建议不能修改真实业务状态。
- 司机重复点击不会形成重复派单。

## 15.3 数据可信性

- 订单尺寸未知不得自动视为零。
- 司机位置过期不得标记实时。
- 车辆容量未知不得自动确认可装载。
- ETA 必须带计算时间和数据来源。
- 设计演示数据必须显著标记 Demo。
- 不完整数据不能作为已验证 live 汇总。

## 15.4 性能

实际接口延迟与求解时间目标在基线压测之后冻结。

建议分别测量：

- 单订单车辆候选筛选。
- 10、50、100 笔订单的批量调度。
- 单条已有路线的插单搜索。
- 三维装箱求解超时。
- 同时调度员数量增加时的响应。
- 路网时间矩阵调用缓存与失效。

没有基准测试前，不承诺任意规模下的实时最优解。

# 16. MVP 开发计划

## Gate R0 — 技术与数据契约

交付：

- 产品范围冻结。
- 核心数据模型。
- 车辆及货物字段定义。
- 服务等级和调度规则。
- 开源技术选型报告。
- 受控测试数据集。
- API 契约与权限边界。

**验收：**无需启动真实业务服务，也能使用固定样例完整计算订单装载条件和路线可行性。

## Gate R1 — 人工调度闭环

交付：

- 订单录入。
- 车辆和司机管理。
- 手工派单。
- 接单。
- 取货。
- 配送状态。
- 签收凭证。
- 异常记录。

**验收：**使用测试订单完成从创建至签收的闭环，且重试不会重复派单。

## Gate R2 — 智能推荐调度

交付：

- 车辆筛选。
- 载重及容积初筛。
- 及时送时间窗校验。
- 路线及 ETA。
- 推荐车辆排序。
- 关键原因解释。

**验收：**超载、车型不匹配、时间窗不可行等方案被拒绝；推荐方案可以追溯所用的车辆和路网数据。

## Gate R3 — 顺路拼单 MVP

交付：

- 现有路线读取。
- 取送点插入。
- 各路段剩余容量计算。
- 原订单时间窗重新验证。
- 新增绕行和成本计算。
- 司机确认及插单提交。

**验收：**可行拼单成功；超时、超载、冲突和重复提交均正确拒绝。

## Gate R4 — 复杂货物装箱

交付：

- 大件货物尺寸校验。
- 3D Bin Packing。
- 摆放与堆叠限制。
- 装箱结果可视化。
- 人工装载复核。

**验收：**长板材、柜体、门窗和混装货物不能仅因总容积足够而被错误判为可装车。

## Gate R5 — DR 仓配与三维展示集成

交付：

- W1/W2/W3 调度状态摘要。
- 车辆与运单可视化。
- 调度地图。
- 及时送与异常指标。
- 只读数字孪生对接。

**验收：**真实与演示数据清楚区分，三维刷新不能修改运营状态。

# 17. 必测验收案例

| 编号 | 输入场景 | 预期结果 |
|---|---|---|
| AT-01 | 货物总体积超过剩余车厢容积 | 拒绝车辆 |
| AT-02 | 货物未超体积，但单件长度超过可装载长度 | 拒绝或转人工复核 |
| AT-03 | 体积合适但重量超载 | 拒绝车辆 |
| AT-04 | 货物不能堆叠，现有装载方案需要堆叠 | 拒绝方案 |
| AT-05 | 及时送在承诺时间内可完成 | 返回可行车辆 |
| AT-06 | 插单导致已有及时送超时 | 拒绝插单 |
| AT-07 | 顺路插单不超时、不超载、司机确认 | 创建有效配送任务 |
| AT-08 | 中途取货后某一段车辆容量不足 | 拒绝插单 |
| AT-09 | 司机接单时路线版本已过期 | 拒绝旧方案并重新计算 |
| AT-10 | 两个调度员同时确认同一互斥任务 | 只有一个提交成功 |
| AT-11 | 司机签收请求重复发送 | 只产生一次有效签收 |
| AT-12 | 司机位置过期 | 标记位置未知，不宣称实时 ETA |
| AT-13 | 地图服务异常 | 返回明确故障或保守降级，不伪造路线 |
| AT-14 | 跨公司读取车辆或运单 | 拒绝越权访问 |
| AT-15 | Demo 订单进入运营大屏 | 显示模拟标识，不计入真实指标 |
| AT-16 | 车辆装载空间未知 | 不允许自动确认可装载 |
| AT-17 | 司机拒绝顺路插单 | 原运输任务保持不变 |
| AT-18 | 已签收运单重复改派 | 按状态规则拒绝 |
| AT-19 | 异形建材无法由装箱求解器证明适配 | 转人工装载复核 |
| AT-20 | 所有车辆均无法满足及时送承诺 | 返回无可行运力，提示调度员处理 |

# 21. 最终验收目标

V1 必须证明以下业务能力成立：

**业务闭环：**一笔测试货运订单可以被正确创建、派车、接单、取货、运输、签收及追踪。

**装载正确：**不能派出明显超载、超容积、尺寸不合适或违反装载规则的车辆。

**及时送保障：**调度方案不得为了提高拼单收益而违反已承诺的时效。

**顺路拼单：**新的取送货点可以被合理插入已有路线，所有受影响订单的时间窗和容量约束重新验证。

**数据可信：**无真实来源的数据不得伪装成实时运营数据。

**系统安全：**任何越权、重复派单、错误签收和真实业务状态污染均属于阻断问题。

**工程交付：**代码、测试、审核、集成、上线是不同状态，全部绑定可核验的 GitHub 提交版本。

**产品最终目标：建立一套以“及时送优先”为核心、以车辆实际装载能力为约束、以顺路拼单提高运力利用率的 DR 智能物流调度系统。**

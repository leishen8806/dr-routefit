# DR RouteFit 配送交互原型 · R1 / R1-M

v0.1 · 本地高保真功能原型。沿用现有 Logo 与设计标准，使用合成数据，不连接生产系统。独立原型实现不代表 D24 正式技术选型。

## 启动与打开

在项目根目录运行：

```powershell
node E:/Dr.RouteFit/prototype/server.mjs
```

浏览器打开 [本地原型](http://127.0.0.1:4173/prototype/)。服务仅监听本机；无需安装依赖。使用 HTTP 启动，不直接双击 index.html。端口已运行时直接打开链接，不重复启动。

## 推荐走查顺序

1. 调度：新建订单并保存草稿；可先尝试空表单验证。填写合成客户、地址、货物、尺寸、重量、件数、时间、USD 运费和现金方式。
2. 调度：确认报价与人工承诺，填写核验依据并勾选地址、实测、客户确认；选择车辆发送提案。
3. 上方切换司机：接受任务。
4. 切换仓库：逐项复核装载、包装和件数，填写演示放行凭证，准备交接。
5. 切换司机：逐件点收取货、出发、登记现金收款、记录签收。
6. 切换财务：核验收款，填写演示现金核对凭证。
7. 切换司机提交交款，再由财务核对结清。订单送达不会自动结清收款或交款。

提案演示 TTL 为 120 秒，过期回待派，保留原承诺。顶部切换器只为原型评审，正式应用不会用它代替登录权限。

“原型检查”提供状态切换与重置。转账流程须财务核验后再签收；部分签收进入退回，调度授权后司机返仓，仓库准确点收才结案。离线模式只允许收款／签收证据暂存，再从“同步与消息”恢复上传；版本或状态冲突不能强行覆盖。

## 数据与实现边界

- 实现自营 R1 与合作车辆／人工快递 R1-M 切片：USD 运费、合作应付、现金／人工转账核验。COD、KHR、月结、中控、自动推荐不在本轮。
- 当前会话的 sessionStorage 保存合成数据，刷新保留，关闭会话后不承诺持久化。重置会清除演示进度。请勿输入真实个人、银行或客户数据。
- 凭证以演示编号输入，不采集真实照片、签名、定位或银行流水；地图为标注清楚的路线示意，没有真实 ETA。
- 角色、幂等、并发版本和业务约束在 mock service 中演示；浏览器持有全部演示数据，不是安全后端。生产须服务端重建授权、事务和审计。
- 源代码：app.mjs 为共享 UI；model.mjs 为状态与规则；app.css 为视觉 token 和布局；server.mjs 为本地静态服务。
- 设计与交互契约见 PROTOTYPE-CONTRACT.md、DESIGN.md；不改动 PRD、四份标准和现有品牌资产。

## R1-M 走查入口

1. 调度 → 合作方准入：分别审核合作车辆 P01、承运方 P02，填写核验凭证并确认资格、能力与窗口。新登记合作方保持待核验。
2. 合作车辆：调度选择待派订单 → 选择合作车辆 → 合作司机确认窗口与持货 → 仓库复核 → 合作司机取货、出发、收款签收 → 财务核验。部分签收走调度授权、司机返仓、仓库点收。
3. 人工快递：调度建立委托 → 人工联系 → 承运确认 → 安排交接 → 仓库逐件交接 → 调度录入原始承运事件 → 独立核验 POD。未知／乱序事件只留档，不把报告送达当成核验结论。
4. 取消待确认不能重新派单；交接后退回须记录负责人和期限，承运确认、到仓和仓库准确点收分别完成。
5. 财务 → 合作方应付：核对、争议、部分付款、冲正与重新核对。客户应收与合作应付分别留账；取消委托不擅自抹掉已确认费用。

合作司机演示身份固定为 P01 / Dara；新增合作车档案不自动生成登录身份。车型门洞与箱体尺寸是固定演示参数（180×180 / 320×180×180 cm），正式准入须对真实车型版本建档。快递无虚拟车辆，也不接入第三方 API。承运事件时间按金边时区输入；相同或更旧时间保守标为迟到，需人工核对。

调度工作台支持繁忙场景（基础 3 单＋8 笔合成订单）、紧急事项直达订单和阶段筛选。原型重置后可点‘补充繁忙演示数据’恢复；不会覆盖已有进度。规则与验证见 records/2026-10-24-dispatch/README.md。

调度首页现分地图调度、订单队列、异常待办、运营概览四个 TAB；默认地图，点击车辆或选择订单可进入调度操作。地图均为演示位置，完整变更记录见 records/2026-10-24-dispatch-map/README.md。

事故应急入口：调度选择在途车辆订单 → 车祸／事故应急转运。按件分配给多辆空闲合规车辆，逐车接受、现场交接、签收或返仓；原单保留财务与承诺。范围、候选资源与验证见 records/2026-10-24-incident/README.md。

## 仓配一体与双工作区扩展 · 2026-10-24

一个平台、两类工作区，共用订单与主数据。点击左侧“运营中心”进入商品、库存、车辆、司机、运费分成和提现管理；“调度中心”进入地图与履约。角色切换仅为演示，不构成真实认证。

用户已确认：司机可申请提现，由财务人工审核；平台与司机按订单配置比例分成，不设默认正式费率。操作路径：

1. 运营 → 商品与货品：维护 SKU、单件包装长宽高、重量和状态；仓库与库存 → 登记入库，查看合格、预留、可用、待检及流水。
2. 车辆管理：维护载重、箱体尺寸/容积、门洞、绑定司机与维护状态；有任务时禁止修改。司机档案：登记合成身份及驾驶资格、人工核验；司机“我的”提交银行名称、演示户名及后四位，财务审核。
3. 调度新建订单：可关联商品和出库仓；普通配送或额外付费的独享闪送，分别输入基础运费、附加费、平台比例。承诺闪送须明确确认费用、独享车辆及人工时限。不自动承诺固定送达分钟数。
4. 关联商品在承诺时预留，实际交接时出库；退回进入待检区，由仓库质检放行后才回可用。事故接驳不重复出库。
5. 完整送达、客户收款核验、现金交清后，财务 → 运费与分成 → 订单分成 → 订单核对 → 确认分成入账。
6. 司机 → 我的 → 提现：申请冻结余额；财务 → 提现审核：审核/驳回，审核后登记人工付款。驳回释放余额，在途申请禁止换卡。司机代收客户款与收入分账。

所有后台业务页采用独立菜单、列表/详情或业务标签；历史明细使用有界滚动或折叠，避免列表下继续叠完整档案。完整订单详情里的履约、资金、事件、快递、应急分开显示。

新增模块 platform-model.mjs / platform-ui.mjs 复用现有动作接口与本地状态。52 项模型测试通过；browser-warehouse-platform.js 验证 7 组新流程，原有 R1/R1-M/事故/地图回归保留。详见 [本轮记录](records/2026-10-24-warehouse-platform/README.md)。

这是扩展交互原型，不修改 PRD V1.4、规则/验收编号、四份 v0.1 草案或既有 Logo。生产数据库/API 尚未补充本轮库存、身份、分成和提现契约；原型不含真实银行、GPS、实名认证、商城、采购、库位波次或自动计价。合作费用与事故多车费用仍走独立核对，不重复进入普通司机钱包。

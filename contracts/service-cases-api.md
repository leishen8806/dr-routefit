# 已确认订单服务申请接口 · v0.1草案

2026-10-25。新增5个仅本机开发可调用的服务申请操作：客户可登记地址、时间、退回或费用争议申请；运营可查看并由不同人员受理。它只保存申请与受理决定，**不直接改订单、路线、报价、收款、核销或承诺**。

| 操作 | 权限 | 结果 |
|---|---|---|
| `POST /api/customer/v1/service-requests` | `portal:cases:create` | 创建版本1申请，使用订单当前版本和幂等键 |
| `GET /api/customer/v1/service-requests` | `portal:cases:read` | 只读本货主授权申请，签名游标分页 |
| `GET /api/customer/v1/service-requests/{caseId}` | `portal:cases:read` | 只读单项授权投影 |
| `GET /api/ops/v1/service-requests` | `cases:read` | 运营队列；仍受企业与对象范围限制 |
| `POST /api/ops/v1/service-requests/{caseId}/actions/decide` | `cases:decide` | 用 `If-Match: "1"` 独立决定接受、拒绝或要求客户确认 |

## 当前保障

- 地址、时间变更只允许订单处于 `quoted` 且尚无有效执行；改地址必须提供新地点，改时间必须提供新时间窗。
- 创建人和运营受理人必须映射到不同自然人；数据库触发器与服务端双重阻止同人自审。
- 申请、决定均为只追加记录；跨企业或无客户授权时返回404，不泄露对象是否存在。
- 决定接受后状态只进入 `accepted` 或 `needs_customer_consent`；新报价/财务单据引用是待后续受控领域动作产生的关联，不能伪造生效。

## 候选重报价、价差与原收款边界

运营可对 `ACCEPT` 状态的地址/时间申请，使用既有 `POST /api/ops/v1/orders/{orderId}/quotes` 并附 `serviceCaseId` 生成候选重报价。服务端重新检查区域/受理依据，冻结候选订单快照，并返回 `amendment.differenceMinor` 与方向。每个案件只能生成一份候选报价。

候选报价和其客户确认都是**同意证据**，不替换原订单的当前报价，也不改变原银行收款、原核销、付款准入或已承诺事实。确认候选报价时，系统冻结并显示原报价、候选报价、原已确认收款、有效原核销、未分配原款、待补款和待处理贷项；这样不会把已确认的收款错当作已覆盖新金额。

下一批必须把该冻结位置接到独立的价差应收/贷项与原收款分配映射：补款仅能引用已核验资金事实，降价不能伪装成已退款，任何真实退款仍须单独的付款与银行结果证据。当前不解除确认报价锁、不删除银行事实、不自动退款。

验证：真实PostgreSQL集成测试覆盖同键重放、RLS隔离、同人受理拒绝、独立决定及订单/报价未被直接改写。KESS、真实支付、退款与生产身份均未接入。
